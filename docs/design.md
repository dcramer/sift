# Design system

The dashboard is built from one small set of parts, in `web/src/system/`. Every part, in every state, is on the specimen page: open the dashboard at `/system`. It needs no sign-in: it shows only made-up examples and asks the server for no data.

![The specimen page](images/design-system.png)

## What it is going for

A proof sheet on a dark desk: ink on near-black, one highlighter pen, hard edges. Calm. Weight and size do the work.

- **Dark only.**
- **Two colours mean something.** Yellow (`highlight`) means "look here": the name, the current section's mark, the headline figure, what is waiting on the reader, a search match, the label Activity is narrowed to in its chart. Red (`destructive`) means a failure, or deleting what nothing brings back (`DeleteButton`). Nothing else is coloured; everything else is the ink colour at some strength.
- **As little chrome as it takes.** Nothing on the page has a fill of its own: a list sits straight on it, and a sheet is set apart by a thin frame alone. Only what floats above the page (a panel, a dialog, a menu, a toast) is filled, so it can cover what is under it; the design-system test fails on a surface fill in any other part, and the theme has no grey surface tokens to reach for. A sheet is for a group of settings, not for a list. Inside it, space and type separate things before any line does. Controls are filled (`--fill`), not outlined. Notes and headings have no box and no rule. The only lines inside a sheet are faint dashes between rows (`--rule`).
- **Lines are ink, thinned.** `--frame` for a sheet's edge, `--rule` between rows. Never a separate grey.
- **One shadow.** `--edge`: hard, offset down and right, the edge of the sheet beneath. It belongs to sheets and to what floats (a dialog, a menu). Buttons have none: the highlighted button is a flat stroke of yellow, like the name. Any other shadow fails the design-system test.
- **One word for each thing.** What Sift does with mail (Keep, Archive, Digest, Spam, Block, Leave in inbox for mail left alone without a label, Unlabelled when no tier was sure which label), where a decision got to (Suggested, Done, Undone, Not done…), how a sender and the reader know each other and which tier decided each have exactly one name, kept in `web/src/lib/format.ts` and used in every filter, select and column. What Sift does is its icon and its word (`Does`), and only the action: "Archive", never "Archive + unsubscribe"; what comes with an action is said where the label or rule is edited. A verdict is the action, then the label: "**Archive** as Marketing". A sentence uses the matching phrase (`willBe`). Never write one of these words in a view.
- **Say what the reader can use.** A list shows what something is, what Sift said, why, where it got to and when. Model names, token counts, cost per message, confidence and change ids belong in the reader's history, not in a row.
- **Corners are small and even** (`--corner`, 3px) on everything you press or type in. Only the highlighter stroke and the wordmark are cut by hand (`--cut`). Surfaces are square.
- **Type is by role, set as Peated sets it.** Karla carries everything read. Hanken Grotesk, bold, is for what is named or counted: the splash's one line (`.display`, 44 to 88px), a page's title (`.statement`, 32 to 40px), a dialog's (`.title`, 26px), a section's heading (`.heading`, 22px, clearly larger than a name so it never reads as the first row), names (`.name`), figures. Display type is tracked tight, tighter as it grows (−0.02em for a name to −0.04em for a title and −0.05em for `.display`); that is most of what makes it look set rather than typed. A figure's label (`.slug`) is Karla at the supporting size in lighter ink. A column head (`Th`) is Karla in capitals, 11px semibold, a little tracked, in quiet ink: the one thing under 12px, since capitals read larger than their size. IBM Plex Mono is for anything typed or pasted, and nothing else. The wordmark alone is in Bricolage Grotesque. Text is 16px (`text-base`), what supports it 14px (`text-sm`, what is typed or chosen in a control too, but 16px on a touch screen, where a phone zooms in on a smaller input), an opened message 17px (`text-reading`), keycaps 12px (`text-label`), column heads 11px (`text-head`, `Th` alone), and nothing else under 12px. The pages before the dashboard (`Entry`) set their supporting text at 15px and their controls at 40px. Those are the only sizes a class can set; titles, figures and the wordmark are role classes. A size typed by eye (`text-[13px]`) fails the design-system test. A button's words are semibold; a select's value is not.
- **One height for controls.** Everything pressed or typed into in a row or a toolbar is `--control` high (32px), so buttons, selects and inputs line up. `lg` is for the one action a screen is about. Somewhere to type (an input, a text area, the search bar) is outlined and empty; anything pressed, a select included, is filled (`--fill`), and stronger on hover. A button is a verb in semibold; a select shows its value in regular weight beside a chevron, so the two never read alike. What cannot be pressed now is not filled: a disabled button is an outline in quiet ink, and a quiet one dims.
- No app bar, no gradients, no pills, no icons as decoration. An icon that names something (an action in `Does`, a section in the rail, always with its name under it) is not decoration. The one decoration is a doodle where a screen has nothing else to show, drawn as [brand.md](brand.md) says.

Tokens and the role classes are in `web/src/index.css`.

## Parts

| Part | Use |
| --- | --- |
| `Button` | `mark`: what the screen is waiting on, one per screen at most, never down a list. `ink`: what finishes a dialog or form. `plain`: a page's own action (adding to its list),  and anything else said once. `quiet`: repeated down a list, firmer when its row is pointed at, and ways out. `danger` and `destroy` are `DeleteButton`'s alone. With `href` it is a link. `busy` while a press is being acted on. `Finish` is the `ink` press that finishes what is written in a layer (the composer's Send), which ⌘↵ or Ctrl ↵ presses from anywhere in it. |
| `DeleteButton` | Every press that deletes what nothing brings back: a rule, a label, a model sign-in, a mailbox, the account. Its words in red with an ellipsis, or down a list a quiet trash can like the row's other actions, so a list is not striped red. Either opens the same question: a dialog titled with it ("Remove this rule?"), what it is under that when the title does not say, what else goes that the reader could not tell (a rule's Gmail filter, a label's rules), and the press that does it, filled red with the same words. With nothing to type, that press has the focus. Deleting a mailbox or the account, which takes the record of mail with it, asks for the address typed first. A failure stays in the dialog. |
| `ConfirmButton` | A press that is hard to take back but deletes nothing (turning Sift on). It asks in place, with the same words on the button that does it. |
| `Select`, `Input`, `TextArea`, `Check` | Controls. `Select` is for a short list; `icons` puts an icon before a choice (an action's, from `ActionIcon`), in the list and once chosen; `face` draws something else in its place where a control's width does not fit (the rail's `MailboxSwitch`). |
| `ChoiceGroup` | A few choices seen at once, one on: where a sender stands, how to read a message (Text or HTML). `clearable` when none is a choice too. With `notes` they are rows, each with a quieter line saying what sets it apart and a tick on the one that is on: a model and what it costs. |
| `Field`, `Form` | A form is a column of fields with what finishes it last. A field is its label, its controls, what follows from the answer (`hint`) and what is wrong (`error`). `inline` puts the label beside the controls, for a short form in a narrow column. |
| `FieldGroup` | A long form in parts, each under its name (`.name` size), a rule above every part after the first: the rule dialog's Which mail, What it is, What happens, in the order a rule applies. Not for a short form; on a phone it is what keeps a long one readable. |
| `Rail` | The sections, down the left of every screen on a desktop (from `md`, where the rest of the system leaves its phone layout: at least 48rem wide and 30rem tall, so a phone on its side keeps the phone's layout, which `phone:` names). No fill: a `--frame` line sets it apart, as tall as the window and staying put while the page scrolls. The name at its top, linking to the first section; with Inbox on, Compose under it, a filled press shaped like a section, with no keycap (`?` lists `C`); then each section as its icon over its name, the current one's icon in a stroke of highlighter; For review's count a bubble in ink on its icon's corner, so the icons stay in one column. At its foot, Sift's line stacked (`components/status.tsx`: a sync icon over how long since it synced, each mailbox's time when pointed at; then the model's cost over 30 days, `$4.12` over `30D`, which previews the time Sift saved over 24 hours, 7 days and 30 days with its trend, then the cost over the same windows, and links to Activity), then the `MailboxSwitch`, then who is signed in, as an `Avatar` that opens a `Menu`. The line counts on by itself, by the minute, never the second. Given no sections it is the name alone: the page before it knows who is signed in. |
| `Masthead`, `BarSlot` | The top of every screen on a phone, where the rail is not shown (see Narrow screens). `BarSlot` is its room for a list's search, given by whatever draws it. |
| `MailboxSwitch` | Which of the person's mailboxes every list shows, for someone with more than one: a `Select` of All mailboxes, set apart, then each address. Kept in the browser, not the address or the server: it is the reader's convenience. Every read under it asks for that mailbox alone, and a mailbox that is no longer theirs is All. In the rail, beside whose mailboxes they are, it is an icon (several envelopes for All, one for a mailbox) over All or the address cut to the rail's width; the choices say themselves in full. Sift's line above it, Settings and the account stay for all of them. |
| `Notice` | A state of Sift itself, true on every screen, at the top of the page over its title: Sift cannot be reached (plain ink, a pulse: it mends itself), a sign-in has expired or Google will end it within two days (`look`, with a link: the reader mends it). |
| `PageHeader` | The top of every page: its title, and on the right the page's own action or one quiet line of numbers, centred on each other. No count beside the title (the sections have it) and no sentence under it that says what the page is or how to use it; `meta` is only for naming the page's subject, such as a sender's address. While the dashboard is narrowed to one mailbox, its address follows the title, so a list that looks short says why. |
| `Section` | A part of a page or a panel under its own heading, with a count and at most one action beside it. Space sets it apart. |
| `ListPage`, `ListView`, `FilterGroup` | **How every screen shows many of one thing.** `ListPage` is the page header with the page's own action, drawn by the screen's route on the server; `ListView` inside it is the list. Its search and filters are kept in the address (`useParam`), so a narrowed list can be bookmarked. Anything the page shows first (`intro`), one outlined bar holding the search and the Filters button, then the rows. `view` adds a few ways to see the list as segments at the end of the bar (Activity's Changed and Everything); use it for whole alternative lists, filters for narrowing one. The filter button opens a panel on the right that pushes the list left. Filters that are on show as a count on the button and, when the panel is closed, as a line of chips that each clear one. While rows are selected (`RowCheck`), `selected` puts what to do with them in the search's place: how many, a quiet press with its key for each, and Select none; the rows do not move. |
| `Pager` | Under a list too long for one page (Activity, Contacts): which rows these are of how many, then Newer and Older. The page is in the address (`?page=2`), and narrowing the list goes back to the first. Nothing while the list fits on one. A list read as it is scrolled (Inbox) has `More` instead. |
| `Table`, `Heads`, `Tr`, `Th`, `Td`, `TrGroup`, `Sub`, `OnPhone`, `RowActions`, `RowCheck` | Rows of the same kind of thing, one row per item: the only way to show a list. No surface of its own; on the page a row reaches a little past its text on both sides (`--bleed`), so the hover has room around what it holds, while the rule under it stays in line with the text. `Tr onOpen` makes the whole row pressable; the row the keys are on is a stronger fill, never an outline. `Sub` is a quieter second line in a cell; cells sit in the middle of their row, so a one-line cell beside a two-line one lines up with the pair. `RowActions` is the last cell: quiet presses that act without opening the row, always visible. Every table has `Heads`, one `Th` per column. A list that reads as plain rows keeps them for screen readers alone; one with two figures or dates beside its first column shows them (`shown`), as Rules and Labels do, since a number alone does not say what it counts: `wide` where a phone drops those columns, `always` where it keeps some. On a page of several tables in one layout (Labels) only the first shows them. A head or a cell takes `says` for a `Tooltip`; nothing marks that it has one. `TrGroup` heads the rows after it, such as a day, inside the one table, so J and K and the columns run through every group. `RowCheck` is the first cell of a row that can be selected with others for a press on all of them (Inbox): a check, and X on the row the keys are on; pressing it never opens the row. |
| `AnswerPicker` | Saying what a message is: a dropdown that starts on the reader's answer where they gave one, else Sift's label: Leave in inbox first, set apart, then what else it might be (each with a `Meter`), then every other label, and last a way to add a label; and a check that agrees. Picking from the list is the answer, so agreeing is one press and a change is two. The answer on every For review row and in the reader's `AnswerRow`; it is sent only when its toast goes, so Undo has nothing to take back. |
| `Meter` | How sure Sift is of a label, in three steps of ink, before the label it qualifies. Its name (Unsure, Fairly sure, Sure) is read out; the steps come from `sureness` in `lib/format.ts`. Full means Sift does it by itself while on; mail it would hold is never full. Before Unlabelled in a column of answers it is the bars' room alone, so the words line up. |
| `Facts`, `Fact` | What is known about one thing, as terms and values: a sender. Leave a fact out rather than give it no value. |
| `Timeline`, `TimelineEvent` | What happened to one thing, oldest first, each with at most one press (Undo). |
| `Splash` | The first page of someone not signed in, in place of `Entry` while sign-in can start: no sheet, the name at the top left, one `.display` line, then a sentence and the one `mark` button. Terms, privacy, security and a link to the source at its foot. On a phone the line fills the width and everything below the name sits at the bottom, over the links, with the button running the width under the thumb. It is also the page while Sift cannot say who is signed in: what a deploy still needs, an error, offline, and a `Blank` for the line while a slow load finishes. |
| `Entry` | The page in place of the dashboard when sign-in cannot start here. One sheet, centred, the name across its top edge; under it the terms, privacy and security links. A statement says what is needed, one line says why, then where to go (a button per address) or what to run (`Copyable`). |
| `Onboarding` | The page in place of the dashboard while someone sets Sift up: connecting a model, saying what they want, choosing their labels, going through older mail. One column about 46rem wide, centred, with the name and who is signed in (Settings, Sign out) along its top; the steps above the title, those done ticked and the current one underlined in the highlighter; a title, one line of what the step is for (onboarding, so it explains), the step, and one `mark` button with at most one quiet way out. No frame: a step as long as eight labels scrolls the page. On a phone the steps become "Step 2 of 4" and the step's name. |
| `Sheet`, `SettingRow`, `SettingsGroup` | A group of settings, framed. Each row says what it is, what follows from changing it, and holds its control. Not for a list. A settings page is `SettingsGroup`s: the group's name and what it governs on the left, its sheets on the right, a rule between groups; on a phone they stack. |
| `Figures`, `Figure` | Headline numbers, straight on the page. `look` for the one to see first; `href` links to the list it counts. `compact` for a column as narrow as a card: the figures at a name's size, in even columns. |
| `Spark` | How a figure moved over the days behind it, as one line of ink with no axis, the first and last day under its ends. Under the figures it trends, never alone: the shape, not values to read off. |
| `StackedBars` | Counts over time, stacked by series, on the left axis. `line` adds a second measure (model cost) on its own right axis; both start at zero and share their gridlines. No legend: pointing at or focusing a column opens a tooltip with that day's figures, the segment under the pointer in bold. `compact` beside figures. |
| `Swatch` | A series' or a tier's colour, always beside its name. |
| `Share` | How much of a whole one row is, as a thin bar along it (a label's share of the mail, how far going through the inbox has got), with the figure beside it in words. For comparing rows at a glance, not for reading a value off. |
| `Panel` | One item from a list, opened beside the list: it slides over from the right, three quarters of the screen, so it covers a smaller screen (`narrow` for a few facts and a short form, such as a label), with previous and next in its footer to step through the list, and above them, in a footer of their own that stays while the rest scrolls, what is done to the item itself (`actions`): what changes it first, what deletes it alone at the right. A section's own action stays beside its heading. Below a large screen the header scrolls with the rest, so however tall it is the body has the screen, and Close stays in the corner. Inside a panel, as on the page, a table's text lines up with the headings and its rows reach past it. Settings is one, opened from the account menu over any screen, setting up included (`?settings=1`). So is a new message (`Composer`, `views/composer.tsx`, `?compose=new`), narrow: From when there is more than one address to send as, To, Cc behind a press, Subject, then the text at reading size; Send (`Finish`) and Discard in its footer. A panel written in starts on its first empty field (`focus`); any other takes the focus itself. A message is not one: it opens in the `Reader`. |
| `Reader` | A message, opened from any list, in the list's place inside the frame, the rail kept (`views/reader.tsx`): the list stays on the page, hidden and deaf, so Back (or Esc) finds it as it was, scrolled where it was and with the focus on the row of the message last shown. The address is the list's own with `?message=` (and from Inbox `&thread=`). From the top: `ReaderBar`; the subject as the page's `.statement` heading; `AnswerRow`; then the conversation (`MessageStack`) and what answers it at its foot (`Presses` for Reply, Reply all and Forward, or a `ReplyBox` in their place). The page scrolls as one: nothing in it scrolls inside but a message's own HTML (`MailFrame`). Everything is a reading column 46rem wide. `side` is a column beside it from `xl` and under it narrower, for what is said about the message rather than in it: For review and every list but Inbox put What Sift saw, the sender (All their mail), what else of theirs waits and the history there; Inbox has none, and the sender's details are their name, a link. It takes the focus as it opens. |
| `ReaderBar` | The reader's top line: Back by the list's name, with Esc; the presses on what it shows (Inbox's Archive, E, and Mark unread, ⇧U); where it is in the list ("3 of 12"); previous and next, chevrons with K and J (← and → too). On a phone it is one line, without keycaps: Back as its arrow, the presses, previous and next; nothing wraps. |
| `AnswerRow` | Sift's part of the reader, on one line under the title: the `AnswerPicker` (with its agree check), Why, and Rule… (`Make a rule…`), which opens the rule dialog. Why opens what Sift said under the line: its reason, Keep as …, and in Inbox the history. It starts open where answering is the job (For review and every list but Inbox). On a phone the picker takes what the presses leave. |
| `MessageStack`, `MessageHead` | A conversation, a thread read by scrolling the page, oldest first: each message open, at reading size under its `MessageHead`, or folded to a row of who sent it, its first line and when it came (`Heard`). The account's own messages say "me", in the head and in who they went to. The head: the sender's name (a link to their page, with `ContactHint`), their address (not on a phone), when it came, short (`Heard`: the time today, then the day and the time, the year only when it is not this one), and at the end, where the reader may write, Reply and a menu of Reply all and Forward for answering that message; who it went to under them (`SomeOf`) unless only the account. A press on a folded row opens it in place, a press anywhere on an open one's head but a link or a button folds it, so several are open at once. Past five messages the middle folds into one "N more" row, keeping the first and the last two; open ones stay out of it. One message alone is open and does not fold. Rows divided by the dashes, an open message standing between runs of folded ones. On a phone the head keeps to one line, the name giving way. |
| `Presses` | A few presses on what the reader shows, each with its key, on one line: Reply (R), Reply all (A) and Forward (F) under the conversation, answering its newest, and Archive and Mark unread in the bar. |
| `ReplyBox` | A reply or a forward written in place, at the foot of the conversation, which stays on the page above it (`InlineComposer`, `views/composer.tsx`), whichever message it answers: which one, in quiet ink, when it is not the newest ("Replying to Ada Lovelace, Nov 18"); its fields, the text, then Send (`Finish`, ⌘↵ or Ctrl ↵) and Discard on a line under them. It scrolls itself into view as it opens, with its first field focused. |
| `Dialog` | A form or a question: adding labels or a rule, applying a rule, confirming a deletion (`DeleteButton`). Centred. `footer` for the actions that finish it. A dialog and a panel are one kind of thing (`system/layer.tsx`): the same dimming behind, header, close button, gutters and footer rule, and a dialog opened from a panel dims the panel. Inside either, `--surface` is the layer's own ground, for whatever has to cover a row there (a `ConfirmButton` question). |
| `Toaster`, `useToast` | What a press did, after the list has moved on: "Archive as Marketing", or what was made or removed said as itself ("Mail from shop.example.com: archive it"), under a `kind` that says what sort of thing it is ("Rule added", "Label removed"), so the reader knows what changed without opening it. No full stop. A slip: the words in a block of their own at the base size, wrapping freely, and the presses on a row under a rule, so long words never crowd them. It floats as a menu does: the raised ground, its frame and the one shadow; in the bottom right corner, and while a panel or dialog is open, above its footer (`AboveToasts`) so Previous, Next and Save stay pressable. Each has a close button. A failure is the same slip: what failed and the error's words under it. Undo is in the highlighter, the one thing on it waiting on the reader; any other press is quiet. A new one replaces the last, so `undo` (Undo, and Z, Gmail's key for it) always takes back the latest; offer it only where the app can really take the change back (a rule just added, unless it replaced one), or hold the change until the toast goes (`onGone`, which also fires when the page is closed or hidden), as an answer does. Gone after 5 seconds, 8 with a press in it; a mouse pointing at it or keyboard focus in it holds it, and nothing else does: Base UI's own timer also stopped while the window lacked focus, which a message's frame takes, so it is off. A failure is set on red, with dark words as on the highlighter (light words on that red cannot be read), and stays until dismissed. Never for something the page already shows, and never for an instruction the reader must follow later: that is a `Note`. |
| `Menu`, `Avatar` | A few things to do, behind one button: under the avatar, who is signed in, Settings and Sign out. An item that cannot be pressed says why under its label. Where a menu chooses how to see a list (`on`), the one showing is ticked. An avatar is the initial of an address, never a picture: the page loads nothing from another origin. Choosing one value is a `Select`, not a menu. |
| `HoverCard` | A link that previews where it goes when the pointer rests on it or it takes focus. Only a preview: a touch screen never shows it, so everything in it is also on the page the link opens. |
| `Callout` | What the reader must know before the page makes sense, first on it: a state Sift is in and how to read the rows because of it (Sift is off: nothing here was done, and what the full meter means). Framed, a highlighted heading, sentences at reading size, a `CalloutKey` per mark the rows use, and the press that leaves the state. One per page at most. It is onboarding, so it explains; it is the one place a page says what its rows mean. |
| `Note` | Said to the reader outside the flow, about the whole page: `plain`, `look` (needs them), `failure`. No box. |
| `Failure` | A press that just failed, under it, or a page that could not load, in the error's words. Renders nothing without a message. The only red a screen writes, and never for what Sift does by itself: it retries that, reports what never lands, and shows it as plain history. |
| `LoadingBar` | A line of ink running along the top of the window while the reader waits with nothing else to show for it: the page while the server draws its frame, a link's screen that was not fetched ahead, data a screen or panel has none of yet (a search, a message just opened). Fades in after 200ms, so what arrives at once shows nothing; a list read again shows nothing. Still and fainter under reduced motion. |
| `Reserve` | Holds the room for something above other content that arrives late and whose height depends on what loads (figures, a chart, a notice that may not be there), so the page below does not move. `room` is its usual height, as classes, so the server's page holds it too. A part that held nothing the last time, in this browser, holds no room: the `sift_empty` cookie names it, and the server reads it. |
| `More` | The end of a list read a page at a time (Inbox): reaching it, a screen's height ahead, loads the next page, whose rows grow the list downward. Nothing of its own shows. |
| `Empty`, `Loading`, `Blank` | What a list shows with nothing in it (say what would put something here), and while rows are on their way. `Empty art` is the whole page instead: a doodle centred in the room the list would take, the sentence at a dialog title's size under it, and `after` for what the reader can still do there (Sift is off, and the press that turns it on). Only where the list being empty is the good news (For review with nothing waiting, which then has no search bar or filters, and no `Callout`: its key explains rows), never for a search that matched nothing. `Loading` takes one row's cells, set as the real row's (the same `Td`s), with a `Blank` for each piece of text; a `Blank` sits in the line its text will take, so the row is the height it will be. Without cells, lines of text, for a panel. |
| `Does` | What Sift does with mail: the action's icon in lighter ink, then its word. Never with what comes with the action (unsubscribe, mark read). Unlabelled (review) is in quiet ink: it is a question for the reader, not a fault, and in yellow it read as one. In a log it says what Sift did with it: "Asked you", since Sift's own Gmail label is a change. `struck` for an undone change. In every list, column and verdict. |
| `Tooltip` | A few words more about what it wraps, when the pointer rests on it: the exact time behind "11 h ago", what a figure counts. **Never on a touch screen**, nor is any other hover (a `HoverCard`, a chart's), so a tooltip only adds to what the page says; what a phone reader needs is where a tap reaches it, such as the panel a row opens. The only tooltip: no element gets a `title`. |
| `Hint` | One thing about what it follows, as a small icon after it, said in words when pointed at (a `Tooltip`). `look` is yellow. A touch screen never shows the words, so what it says is also on the page the name links to. After a sender's name it says how they and the reader know each other (`ContactHint`): new (yellow), you write to them, or they write often and are never answered; nothing for everyone in between. `said` sets the words beside the icon instead, where they are the point: under the name on a sender's own page, once. |
| `Highlight`, `Marked` | A stroke of highlighter; a search term marked in text. |
| `Look` | A word in yellow ink for what is left to the reader, inside a line: "Not sure" in a list. |
| `TextLink`, `Code`, `Kbd`, `Copyable` | A link in text; something typed; a key, as a small keycap (see Keys); a value carried somewhere else whole. |
| `Disclosure` | What most readers never need, folded under the question that leads to it. |
| `SomeOf` | A list said in a line, the first three and "and 38 more": everyone a message went to. The press says the rest where it stands, with Fewer after it, so a message to a mailing list does not crowd a panel's header. On a phone the press reaches past its line for a thumb. |
| `MailFrame` | A message as its own HTML, in the reader, on white paper because email is written for it. It runs nothing and loads nothing from elsewhere; links open in a new tab. ## Narrow screens

Every part has an answer for a phone, and a new part needs one before it is added.

On a phone a row keeps only what identifies it and what it is; figures, dates and who made it go to the panel the row opens, and so does anything that cannot be taken back, so a thumb cannot remove something by brushing a row. A row of mail is the exception for its date: it reads as a mail app's does, three lines set close at the body size: the sender with when it came at the top right, then the subject, then the start of the text with what Sift thinks it is at its end. Unread mail's sender, subject and time are bold and bright; read mail's are plain. Newest first under `TrGroup` headings for Today, Yesterday, This week, Last week and each month before (`period`, `Arrived`), each a small quiet line that stays under the top bar while its rows pass.

## Whatever can be pressed shows the pointer

A button, a link, a row that opens, a choice in a menu or a select, a checkbox with its label: each takes `cursor-pointer`, and loses it only while disabled. Nothing that cannot be pressed takes it.

## Keys

A control asks for its key and draws the keycap itself (`shortcut` on a `Button`, `useShortcut` anywhere else), so a key that is shown always works and a key that works is always shown. Never bind a key with a listener of your own.

- **The keys are Gmail's:** `J` and `K` to move, `Enter` or `O` to open, `Esc` to close, `/` to search, `Z` to undo from a toast, `?` for the list of every key live where the reader is; in Inbox `X` to select, and `E`, `Shift+I` and `Shift+U` to archive and mark read and unread what is selected; in its reader `R`, `A` and `F` to reply, reply to all and forward, and `E` and `Shift+U` to archive and mark unread. Shift makes a letter a key of its own (`Shift+i`, drawn `⇧I`); on anything else it only picks the sign (`?`). With Inbox on, `C` writes a new message from any screen (the rail's Compose).
- **A chord with ⌘ (Ctrl off a Mac)** is the one kind of key that works while typing, since it types nothing: `Mod+Enter` sends what the composer holds. Plain keys never do.
- **The arrows work too, for whoever does not know Gmail's keys:** `↓` and `↑` move down a list, as `J` and `K` do. In the reader `←` and `→` step to the previous and next item, as `K` and `J` do, and `↑` and `↓` are left to scroll the page. One control's keys are one binding (`useShortcut` takes a list), drawn together and on one line of `?`.
- **A keycap** (`Kbd`) sits after the label, outlined; on a filled control it takes that control's ink.
- **Keys are for working through a list**, one item after another: For review, Inbox and Activity (`Table keys`), and the reader they open. Every other list, form and step has none: it is pressed, or tabbed through. Don't add keys to a screen because the parts allow it.
- **Down a list** only the row the reader is on shows and answers to its keys.
- **A layer's own controls are a footer** (`ControlBar`, `Control`), the way a game lists its buttons: the key first, then what it does. A table's (Move, Open, Every key) holds at the bottom of the screen while the table is on the page; a panel's (Previous, Next) runs along its bottom edge, beside where it is in the list, and on a phone becomes wide buttons at the bottom, where a thumb is. The reader's are in its bar (`ReaderBar`), each pressed as well as keyed.
- **What floats is a layer.** With a panel or dialog open the page under it hears nothing; `?` alone works everywhere.
- **Nothing happens while typing** in a field, and Enter never presses a second thing when a button or row already has the focus. A panel takes the focus itself when it opens, not its first button, so Enter presses nothing until the reader moves to something; an answer has no key of its own.
- **Back from the reader leaves the list on the row of the message it was showing**, wherever J and K took it, so the next key carries on from there.
- **No hints on a touch screen**, and the reader can turn keys and hints off in Settings. That choice is kept in the browser, not in Sift: it is about the reader, not the mail.

## Nothing moves after it is drawn

A page is drawn before its data arrives, and what arrives must not push what is already there. Measured as layout shift on a cold load, at desktop and phone widths; keep every page under 0.05.

- A page header that will have a status line passes `meta={null}` until it knows it: the line's room is held.
- A page's action button is shown from the start and disabled until it can work. It does not appear late.
- Anything above other content whose height depends on data goes in a `Reserve`.
- A list's rows may grow downward: nothing is below them. While they load, its `Loading` shows its own rows, not lines.
- Every screen is drawn on the server with its header, its search bar, what is not encrypted (labels, counts, Settings) and placeholders for the rest, so the first paint is the page as it will be, rows to come.

## Rules for adding to it

- A page starts with a `PageHeader`; a screen that lists something is a `ListPage` holding a `ListView`. Don't lay out a heading, a search box or filters by hand.
- A screen's route (`app/`) lays it out and draws its loading rows, as server components; a part that holds state, reads the browser or loads data is a client component in it. Nothing the browser alone knows (the query, the clock, the locale, touch) is read while the page is first drawn: the server's page and the browser's first draw must be the same.
- A list is a `Table`. There are no cards.
- What a press did is a toast. An error that stops a form goes under the form; a failure that stops a page is a `Note`.
- A form that adds something opens in a `Dialog`, and one item is changed in its `Panel`; neither unfolds inside the list.
- Opening an item of a list opens the `Panel`, and the same panel wherever that kind of item appears, so it behaves the same everywhere. A message opens the `Reader` in the list's place, from every list.

- Build screens from these parts. If a screen needs something they cannot do, add or extend a part here, with its states (hover, focus, pressed, disabled, busy, empty, failed), and add it to the specimen page in the same change. A part exported from `web/src/system/index.ts` and missing from the specimen page fails the design-system test, as does a `mark` or `ink` button inside a `Tr` or `RowActions`, or a second `mark` in one screen's file.
- A part says when to use it in its doc comment; that is the line the specimen page shows.
- No inline styles, no fills, frames, corners, shadows or colours written outside `web/src/system/`; red is `Failure` and yellow comes only from a part's tone. If a value is missing, it is a missing token. `tests/design-system.test.ts` fails on any of these and names the file and line.
- Behaviour that is hard to get right (a list that opens, a focus trap) comes from an unstyled primitive, today Base UI. Only files in `web/src/system/` import it (a lint error elsewhere), so the library can change without a screen changing.
- A part's inline `style` is only for a value computed from data (a bar's height, a series colour).
- Motion is short (80 to 150ms): a press, a dialog opening, rows pulsing while they load. All off under `prefers-reduced-motion`.

# Architecture

Sift polls Gmail for new inbox mail and decides, per message, a **disposition** (`keep`, `archive`, `spam`, or `review`) and independently a **subscription action** (`preserve` or `unsubscribe`). It is designed so that most mail never reaches a language model.

## Labels, rules and the cascade

Two things are decided about every message, and they are kept apart.

- **What it is: a label.** A person has one list of labels (`labels`), made by them, for every mailbox of theirs. A label has a name, a description the model reads, a Gmail label, and an action. Rules are the person's too, so a rule decides the mail it matches in whichever of their mailboxes it arrives; only a rule's Gmail filter is per mailbox (`rule_filters`). Before 0048 each mailbox had its own copy of both; that migration made them one set, the primary mailbox's winning where they differed.
- **Labels move mail; Leave in inbox is the rest.** Most labels take mail out of the inbox (archive or spam); one may keep its mail and only tag it in Gmail, when the person asks for that or never wants to miss mail another label might take ("Bills to pay" beside an archiving "Receipts"), but Sift does not suggest sorting the inbox into categories. Mail none of them fits is Leave in inbox (`LEAVE_IN_INBOX`; its id is still `everything_else`, from its old name). It is Sift's own default and nothing about it changes, through the page or the API: it always keeps, has no Gmail label and no description, so mail put there by mistake is where it would have been without Sift. The page draws it as a choice like any label, first in every list of them and set apart, and "(Default)" on the Labels screen. The model knows it as `leave_in_inbox` (`forModel`, `src/triage/prompt.ts`), not by the old id. Moving mail Sift left in the inbox, in Gmail, says only that it is not that, so it is not taken as an answer. Mail to keep from a label is said in that label's description ("not bills still to be paid"), a keep label of the person's own, or a rule (Leave in inbox as its label, so it can carry a condition in the person's words) for one sender. It cannot be removed (`POST /api/labels/remove` refuses it), and the database holds that it always keeps (`labels_everything_else_keeps`). Every other label is the person's. Until they have one, Sift reads nothing from their Gmail: no pass and no going through an inbox (`hasOwnLabels`, `dueWork`).
- **A good label is narrow enough that one action is right for all of it.** Cold outreach is: nobody wants it, and unsubscribing stops the follow-ups. Marketing is not: whether it is wanted depends on who sent it, so the label decides nothing and the real decision becomes a rule per sender.
- **Starting labels are proposed** once the person has connected a model. Sift asks what they want from it, in their own words, and the model suggests labels from that alone, mostly for mail to move (no mail, since none has been read yet). It is a call of its own, not the judge: its own prompt, which says how labels work and what makes a good one (`src/triage/proposal.ts`), its own route (`POST /api/labels/propose`, reaching the model through `Controls`), and its own record (`label_proposals`). Asked once, while the person has no labels: what they keep is made in one write (`POST /api/labels/accept`), after which each mailbox's first pass starts. A mailbox connected later has their labels and rules already, so it is not set up again, and adding it keeps the person signed in as they were. The latest suggestions come back after a reload (`GET /api/labels/proposal`), and Start over asks again from the same words. The action suggested with a label is only a suggestion, as everything is until Sift is on; blocking is never suggested, and Digest is suggested over archive for routine mail where now and then one matters (service notifications). The Labels screen's Add labels starts the same way (describe the mail, keep what fits of what the model suggests, with the labels there are shown to it so it does not overlap them) or by hand.
- **A label is one thing to the person,** wherever their mail is: made (`POST /api/labels/add`) and changed (`POST /api/labels`) once, and listed once on the Labels screen, under what Sift does with its mail, with its figures over all their mailboxes. Names are in Title Case.
- **A removed label stays in the record** (`removed_at`), so what Sift said of earlier mail, and the answers about it, still name it. Nothing offers it again: not the model, not the Labels screen or its limit, not a rule or an answer, and a sender's history shown to the model leaves it out. Removing one (`POST /api/labels/remove`) takes out the rules that name it, with their Gmail filters, and deletes its stored examples; mail still waiting with that label goes back to the reader as mail Sift could not place. The Gmail label stays on mail Sift already moved. A person's last label besides Leave in inbox cannot be removed, since without one Sift reads nothing of theirs. Adding the same name again brings the label back, as what it is described as now.
- **What happens** is the user's to say, never a model's. Usually it is the label's action, one of keep, archive, digest, mark spam, or block; a rule can name an action itself, but never digest or block. Beside the outcome a label can carry extras: mark read (with keep and archive) and unsubscribe. A rule can add either for the mail it decides. "Leave it for me" is not an action: Sift suggesting instead of changing Gmail is a matter of trust, and the only time mail is held for the user is when no tier could place it, the model was not sure enough, or a protection stopped Sift.
- **Digest** is archive, and once a day one message Sift writes lists what it archived ([Digests](#digests)). It is stored as block is: `disposition` archive and `digest` on the label, and on each decision that inherits it (`labelled`, `src/triage/types.ts`), which a rule that gives the label without an action of its own does, and a rule's own action does not. Mark read and unsubscribe go with it as with archive. The database holds that only archive digests and that Leave in inbox never does.
- **Block** is Sift's own, since Gmail's block list is not in its API ([gmail.md](gmail.md)): the message is marked spam, and once that has happened a rule is written so the sender's later mail is that label without a model. Only when the message passed DMARC, so an impersonated sender is not the one blocked, and never for someone the user has written to. A rule may carry the user's own exception to its label's action ("this one is a newsletter, but keep it").

A label's id and Gmail label never change after it is made, so renaming one orphans nothing. An account has at most thirty labels of its own besides Leave in inbox (`MAX_LABELS`): each is a choice the model weighs on every message and the user answers with, so a long list makes both worse.

Tiers run cheapest first. A tier either names a label or abstains; the first answer wins.

| Tier | Where | Cost | Status |
| --- | --- | --- | --- |
| 1. Gmail filters | Gmail itself; runs even when Sift is down | none | built: a rule is copied there when the user asks ([Rules as Gmail filters](#rules-as-gmail-filters)) |
| 2. Rules | `src/triage/stages/rules.ts` | none | built and wired |
| 3. Decision model (Jev / Clef via pi-ai `classify`) | `src/triage/stages/classifier.ts` | ~$0.0001 per message | stage built, provider not wired |
| 4. Model | `src/triage/stages/model.ts`, `src/model/` | one model call | built; in use with Sift off, with a ChatGPT subscription model |
| Fallback | `src/triage/pipeline.ts` | none | built |

Every message is meant to be one of the labels or Leave in inbox. The model gives a label only when the mail plainly is what it describes, since most labels hide mail. When it cannot tell which (its "unsure": it might be one of the person's labels, or whether it is), the answer is `review`: the message stays where it is, gets the review label, and the user is asked which label it is, or adds one. A model call that fails (a provider error, or an answer that is not a usable verdict) is not "unsure" and decides nothing: the message stays in the triage queue and is asked about again on the next pass. After three tries that failed on its own account (`MAX_ATTEMPTS`, `src/store/runs.ts`) the model is not asked again: the next pass runs only the rules on it, and if none decides, records `review` with no label, so it is on For review as Unlabelled like any mail no tier could place. A try counts when no decision came of it: an unusable answer, a provider error while the model answers other calls in the same pass, a call a stopped pass never finished (it is recorded as started before it is made), or a billed verdict whose decision was never recorded. Provider errors that say nothing about the message do not count (they are stamped `retried_at`): three in a row stop the pass asking the model, since the provider is likely down, and errors in a pass where the model answered nothing are an outage too. After that stop, mail that needs the model stays queued, unrecorded, rather than going to a rule that would have deferred to it; mail a rule decides by itself still is. Each call is one attempt with a 60-second timeout and no retries inside the provider's SDK (`src/model/judge.ts`), so a hung call cannot hold up a pass and every attempt is a run of its own. With no model connected, mail no rule covers is not decided at all: it stays in the triage queue (newest first, so it never holds up new mail) and is neither a suggestion nor changed, until a model is connected or a rule comes to cover it.

**A rule** is conditions, then a label, an action, or both. There are three kinds, and a sender or domain can have one of the first two and any number of the third:

- **Conditions → action** ("from this notifications address: archive"). No model. Sift does not say what the mail is unless that costs nothing: another rule that matches names a label. A sender's standing unwanted or blocked is this kind of rule; trusted is a rule for them whose label is Leave in inbox, which every rule that only keeps mail becomes (`leaveInInbox`, `src/store/rules.ts`).
- **Conditions → label**, optionally with its own action in place of the label's. No model.
- **Conditions, when it is label L → action.** It cannot apply until a tier has said what the mail is, so when it is the best match the rules tier steps aside for the tiers that name labels, and `settle` applies it to their decision: the tier's label stands, the rule says what happens. Mail from there that turns out to be something else falls to the sender's rule for all their mail if there is one, and otherwise is as the tier said. With no action of its own it confirms the label's as the user's wish. Like every rule it is made in the rule dialog; "Keep as …" in the reader and a proposal start the dialog on this kind.

Each condition holds one value or several, which are alternatives: mail from either of two domains, or with either of two words in its subject. The sender's address and domain are one condition, so a rule can name an address and a domain together, as are the two ways of asking for a name; different conditions must all hold. The rule dialog shows them as one list of lines, each a kind and a value or an answer about a fact. Any rule may have a name ("Shop receipts"), encrypted like its conditions, which the Rules list, the sender pages and a decision's reason say in place of the conditions; only the rule's panel lists them. The model suggests one only for a rule with several values or kinds of condition. Adding a rule with the conditions of one already there gives it the dialog's name, or none. A standing is read only from a rule for exactly one sender or domain: one that names them among others says how the owner regards all of those, not them.

A rule can ask for the sender's display name, whole or in part, ignoring case and runs of spaces: one address often sends several kinds of mail under different names. Anyone can put any name on mail, so a name is held only beside the address or domain it comes from (`nameAlone`), whose DMARC says who sent it; an exception may name one alone, since its rule names the sender.

The rule dialog opens on the rule in the person's own words, started on what the place it was opened from knows, said as a sentence. Their model fills the form in from them (`POST /api/rules/draft`, through `Controls`, recorded in `rule_drafts`): a few turns with their words and labels and two tools, one that records the rule and one that looks up the senders already recorded in that mailbox by words in their name, address, list or newest subject (`senderDirectory`, searched in memory since senders are stored encrypted). Nothing is made: the person checks the form, which can also be filled in by hand, and adds it. One rule covers every sender named for the same thing; when they want different things for different mail, the first is filled in and the rest said beside it.

A rule can also carry a condition in the user's own words, which only a model can apply; it needs a label for the model to answer with. Rules come from the user (`user`) or from Sift itself (`learned`), only when it blocks a sender; rules made from answers before answers stopped making rules are still marked `correction`. Otherwise Sift proposes one thing only: a rule for a sender whose mail of one label the user has twice in a row given another action than the label's.

There is no tier built into the code that decides what mail is: what decides is a rule the user can see and change, or a model. A message's facts (`src/triage/facts.ts`) are recorded, given to the model, shown when a message is opened, and are conditions a rule can have ("from anyone at this domain, that is not a reply").

Rules that matter across tiers:

- A rule that keeps all the mail it matches is a protection and beats any other rule. Otherwise the most specific rule wins (more conditions, then an exact sender over a domain and a whole name over part of one, then a rule that waits for a label over one that does not), so "this sender when the subject contains X" beats "this sender" whichever was written first. A condition on a fact weighs half of one on the sender, their name, the recipient, the list or the subject, since one fact ("is a reply") takes in mail from anyone: "this domain" beats "is a reply", and "this domain, that is a reply" beats both. A condition with several values weighs what one with one value does.
- A rule Sift made itself (it does so only when it blocks a sender) never hides mail from someone the user has written to; the user's own rules do what they say.
- A rule whose label has been removed does nothing.
- Mail an action rule decides may carry no label at all: decisions, lists and Gmail (which then gets only the mark of what Sift did) all allow for that.
- Errors abstain, and a failed model call decides nothing. Nothing fails toward a mutation.

## Message facts

Every tier, the prompt and the dashboard read one named set of facts about a message (`Facts`, `src/triage/facts.ts`) instead of each re-reading headers.

- **From headers and labels, at sync:** unsubscribe header and whether it is one-click, mailing list id, marked bulk, marked auto-generated, the DMARC, SPF and DKIM results, the bulk mail service it went through (from who signed it, its envelope sender and the services' own headers), whether replies go elsewhere, whether the owner is in To, in Cc or in neither (any of their addresses: the account's, with or without a `+tag`, its dot-variants on gmail.com and googlemail.com, and its Gmail send-as addresses, read on the first sync of each day and kept in `mailboxes.aliases`), whether it is a reply, Gmail's category tab, and Gmail's importance marker (`IMPORTANT`). The marker is Gmail's own guess from how the owner treats mail like it, or the owner's press; the API does not say which, so it is a fact to weigh, never an answer from the owner, and a change to it in Gmail teaches nothing. Mail recorded before Sift read the marker has no value for it.
- **From the whole message, when a model is about to judge it:** whether it has attachments and, from the HTML part (`src/triage/html.ts`), whether it carries a tracking pixel (a remote image drawn 1×1 or hidden), how many sites it links to, whether most links pass through a click-tracking redirect, and whether any link goes to the sender's own domain. These mark campaign mail even when the headers do not. The HTML is kept only where the text is (below), and nothing in it is fetched. Mail a rule decides is read whole only while some rule asks about attachments or a tracking pixel; otherwise it has none of these.
- **From the thread, for a reply a model is about to judge:** how many messages came before it and whether the owner sent one of them: from the record while Inbox has copied the mailbox (`copied`, `recordedThread`), since it then holds the thread's messages and what the owner sent among them; otherwise from Gmail once (`users.threads.get`, labels only: a message the owner sent carries `SENT`), the first read of the thread's other messages, which Sift may never have recorded. Either way the answer is kept in the facts, so a model call tried again asks nothing. No other message's content is read or stored.
- **Recorded** in `messages.facts`, added to when the whole message or its thread adds to them (what an earlier read showed stays), and returned with a message's detail. A message whose whole was read has `hasAttachments`, which is how Sift knows it read it (`neverRead`).
- **The model is told only what is there** (`describeFacts`): the bulk signals on one line, DMARC alone unless it failed, the reply address only when it is another organisation's, Gmail's category, an attachment, and that the sender is the owner or at the owner's own domain (subdomains too, a domain anyone can get an address at never), since mail from colleagues is more often wanted and the same address failing DMARC is a common forgery. Not the tracking and link facts, which repeat the bulk signals and make any click-tracked mail look like phishing, nor Gmail's importance marker until it is measured. Of the sender: how much they have sent and since when, that the owner has written to them (never that they have not, which says nothing), what the owner labelled their mail and, where it differs, their mail under this sender name, and a standing only when a rule sets it.
- **Rules match on them** (`RuleMatch.facts`): each condition is one of the answers `RULE_FACTS` offers for a fact, held by `matchesFacts` against what is recorded, and a fact not known for the message fails its condition. Offered: a one-click unsubscribe, a mailing list, marked bulk, a bulk mail service, DMARC, replies going elsewhere, how the owner is addressed, a reply, Gmail's category, Gmail's importance marker, attachments and a tracking pixel. Left out: counts, the list id (a rule names that), SPF and DKIM (DMARC is the one that proves a sender), and "no tracking pixel", which mail with no HTML could never match. A rule that asks about attachments or a tracking pixel needs the message read, so while one exists each message is read before the rules, model or not, and once for the rules and the model together. A rule with a fact condition cannot be a Gmail filter (Gmail cannot see facts), and anything that acts on a sender's address still needs DMARC, as everywhere.
- **Lists narrow by them.** For review and Activity filter on a few (`FACT_FILTERS`, `src/dashboard/types.ts`) in SQL on `messages.facts` (`factsWhere`, `src/store/messages.ts`), which a GIN index serves.
- **Only what can be checked.** Whether mail reads as AI-generated, and its language, are judgements for a model, not facts.

## Learning loop

Answers become examples the model is shown; rules change only when the user makes them, from a proposal or by hand.

1. Sift proposes a rule when the user keeps doing something to a sender's mail of one label other than what the label does, and the user accepts or dismisses it. Agreement proposes nothing: a model or the user agreeing with a label already gets the label's action, so a rule would change nothing. Accepting opens the rule dialog started on the proposal; the proposal is resolved only by a rule made there (`proposal` on `POST /api/rules`, one transaction), as the user left it. Sift never proposes to stop asking the model about mail a rule waits for a label on: the model agreeing with itself is no evidence, and all it would save is model calls. Someone who wants a sender's mail handled without the model writes that rule. Sift writes one by itself only when it blocks a sender.
2. A rule that Gmail can express is copied to a Gmail filter when the user asks for it. Sift does not promote one by itself.
3. Corrections are detected from Gmail history: the user moving a message back to the inbox or out of spam, archiving or marking as spam what Sift kept, or changing its `sift/…` label, is their answer for that one message ([Teaching](#teaching)). It never makes or changes a rule by itself.

## Gmail

- **Scopes:** `gmail.modify` and `gmail.settings.basic` (`src/gmail/scopes.ts`), and `gmail.send` for a mailbox only once its person lets Sift send from it ([inbox.md](inbox.md)). The first two are restricted scopes, so each user brings their own Google Cloud project with a Web application OAuth client; sign-in is the authorisation-code flow with PKCE, started from the dashboard. Left in "Testing", as a development install usually is, Google limits sign-in to listed test users and ends each one 7 days after it was given, however often Sift uses it ([gmail.md](gmail.md#signing-in) has the modes and what else ends a sign-in). Sift cannot ask Google which mode it is in, so it learns it: a sign-in Google refuses between 7 and 8 days after it was given marks the mailbox (`signInEnded`, `src/store/accounts.ts`), and from then the dashboard says when the current one ends, two days ahead, with Reconnect. Gmail answering more than 8 days into a sign-in unmarks it, as when the client has been published since. So each mailbox's first lapse comes unannounced, as does every one for a sign-in given before this was kept. Signing in again clears the expired status and passes the mailbox at once, without waiting for the next look.
- **Tokens:** each mailbox's refresh token is kept in its person's own database (`credentials`), encrypted when a key is set and bound to that person and mailbox ([secrets.md](secrets.md)). Only `src/gmail/` uses it; the process that starts Sift reads it and hands it over.
- **First connect:** Sift records the current history id and handles mail from then on. It never sweeps the existing inbox unasked.
- **Sync is separate from triage:** a sync pass records message metadata and then advances the cursor; triage works from recorded messages that have no decision yet. Messages are recorded 50 at a time as they are fetched and the cursor moves with the last, so a failed fetch leaves the cursor in place and the next pass reads the same history but fetches only what is not yet recorded.
- **Quota:** every Gmail call waits its turn under its mailbox's share of Google's 6,000 units a minute (`pacer`, `src/gmail/quota.ts`) rather than failing on a 429. The count is in the ephemeral store, so every instance shares it.
- **Change detection:** poll `users.history.list` from the stored `historyId` (2 quota units per call, against 6,000 per user per minute). A new message is not always listed as added ([gmail.md](gmail.md)), so a message history names that Sift has not recorded is new mail if it is in the inbox and arrived since the last sync. A 404 means the cursor expired: read the new cursor, then search the last 7 days of the inbox. History also carries every label change, Sift's own included and with no word on who made it, so `userChanges` (`src/learn/gmail.ts`) cancels each change in Sift's `actions` log since the previous sync began against one matching entry; what is left is the user's. Label changes made while the cursor was expired are lost. Pub/Sub push is a possible opt-in; it still needs the polling fallback.
- **Reads:** once a message ([AGENTS.md](../AGENTS.md#read-gmail-once)). `format=metadata` with named headers for triage, 20 units; with Inbox on, new inbox mail is read whole instead (`getMessage`, 60), its text kept as it is recorded. The body (`getContent`: the text, the HTML part and the content facts) is read only for the model, for mail waiting on the user that Sift never read (a rule placed it), and for an example of mail Sift never read, all through one reader (`readingOnce`, `src/work/bodies.ts`) that looks in what Sift holds first (`heldText`: `mail_bodies`, then `read_bodies`) and keeps what it reads from Gmail before anything uses it: in `mail_bodies` while Inbox is on, in `read_bodies` for 30 days otherwise. So a model call tried on a later pass, the text of waiting mail, an answer's example and Inbox turned on later each find it there. The text of mail an earlier pass left waiting is read before triage (which takes all of every pass while a backlog lasts).
- **Archive** is per message. Gmail shows a thread in the inbox while any message in it has `INBOX`, so a thread stays visible until each message Sift was given has been handled; Sift does not act on sibling messages it did not triage.
- **Digests:** put into the primary mailbox with `users.messages.insert` (25 quota units), which `gmail.modify` allows and which sends nothing: as new unread mail in the inbox, dated when Gmail takes it, with Sift's own `sift/digest` label (`digest` is a name no label of the person's may take). Each is given a Message-ID of its own (`<digest.…@sift.invalid>`), which a retry looks for (`rfc822msgid:`, 5 units) before putting it in again. Sync reads the `Message-ID` header with the rest.
- **Filters:** at most 1,000 per account, one user label each, no update (delete then create), and they act on new mail only. `validateFilter` rejects forwarding, trash, spam and mark-read actions, criteria with no positive match, and a filter for a rule with fact conditions. See [Rules as Gmail filters](#rules-as-gmail-filters).
- **Unsubscribe:** RFC 8058 one-click only (an https `List-Unsubscribe` target plus `List-Unsubscribe-Post`), and only when the message passed DMARC. Never a GET, never a link from the body, never `mailto:`. It is the one request Sift makes to an arbitrary host, so it runs in a deterministic executor; the model never sees the URL.

## The run loop

`sift run` is the one long-running process: it serves the dashboard and ticks every minute. A tick (`tick`, `src/sift/sift.ts`) finds what is due (`dueWork`, `src/work/run.ts`) and begins a Workflow run for each piece: a pass per mailbox (settle unconfirmed actions, sync, then triage every recorded message that has no decision) when a look finds something for it to do (work left in the record, or, once the mailbox's look gap has passed, new mail or a change the person made in Gmail since the cursor, Sift's own changes taken out; [runtime.md](runtime.md#the-core)), each person's upkeep once a day, each person's digests at their digest hour, and, while the person has a model, the next slice of an inbox being gone through and of a test run still going. Workflow delivers each run to the dashboard's server, whose step does the piece (`runWork`). How this runs on a host with no process is [runtime.md](runtime.md).

- **Nothing is queued but runs.** What is due is found in the record and the ephemeral store, so a tick needs nothing from the last, and work left unfinished at a piece's time limit is due at the next. Ticks may overlap: a piece's run holds its key (a pass's names its mailbox by a keyed hash) until it ends, and a piece whose run is under way is not begun again ([runtime.md](runtime.md#the-core)). What a person starts in the dashboard (check now, a test run, going through the inbox) begins their pieces at once, their passes without the look.

- **Off is the default.** Whether Sift is on is each person's own (`preferences.active`), switched under Settings, and a pass changes a person's mailboxes only while it is on. While it is off, decisions are recorded as suggestions (`carry_out` false) and the mailbox is not touched; a suggestion is never carried out later. The exceptions are what the user pressed for in the dashboard: their own answer, and a rule they applied to their inbox ([Teaching](#teaching)). Each is recorded with `carry_out` and `by_user` and carried out on the next pass whether or not they have Sift on. Nothing else is carried out while Sift is off, not even a decision left over from when it was on.
- **Decide, record, then act.** The decision row is written before any mailbox change. Its `outcome` then records what happened: `none` (nothing needed doing), `done`, `skipped` with the reason (left the inbox, spam refused), `failed` or `unknown`.
- **Nothing is dropped.** If the change cannot even be attempted (a provider error), the decision stays unsettled and the next pass retries it. A change that was sent and did not land (`failed` or `unknown`) is left unsettled too, and the next two passes ask again from the labels as they are then (`CHANGE_TRIES`, `src/work/triage.ts`); an earlier try that turns out to have landed settles it `done`. After the third it is settled `failed` and reported to Sentry. None of this is shown as an alert: a change that never landed is a quiet "Not archived" in the message's history. A pass decides each message once; a waiting suggestion gets a further decision only when a rule or a label changes (see Teaching).
- **One account failing does not stop the others.**

## Actions

`src/actions/executor.ts` is the only code that changes a message. Each change follows the same steps:

1. Settle any earlier action on the message whose outcome was never confirmed.
2. Read the message's labels fresh. If it is gone or no longer in the inbox, do nothing.
3. Write the intended change and the original labels to the audit log as `pending`.
4. Send one atomic label change containing only what differs, so unread state and unrelated labels are untouched.
5. Check the labels Gmail answers the change with (it returns them, so they are not read again) and record `done` or `failed`. If the call itself errored, record `unknown`.

`unknown` and `pending` actions are settled by `reconcile`, which reads the mailbox and never replays the change. **In Gmail a message Sift acts on gets two labels:** the one for what it is (`sift/newsletters`) and, when Sift moved it, one for what Sift did (`sift/did/archived`, `sift/did/spam`). The executor adds the second itself, so anything Sift moved can be found in Gmail whatever the caller passed. Mail left for the user gets `sift/review`. Spam is refused unless the sender is known and a search shows the user has never written to them; a failed search also refuses.

Undo reverses exactly what the action changed, keeps anything the user changed afterwards, refuses trashed mail, and is itself an audited action.

## Rules as Gmail filters

A rule can also be written to Gmail as a filter, so it applies when Sift is not running. Only when the user asks, per rule, and only while Sift is on. Gmail's filters are each mailbox's own, so the press writes or removes the filter in every mailbox of the person's (`ruleFilter`, `src/sift/controls.ts`), and each mailbox's is kept track of on its own (`rule_filters`); the rule's panel shows the state that most needs the reader. A mailbox connected after the press does not get the filter until it is pressed again.

- **Which rules.** `filterFor` (`src/triage/filter.ts`, pure) says whether a rule can be one, and why not. A filter runs before Sift sees the message and knows none of Sift's other rules or protections, so a rule qualifies only if the filter could never do what Sift itself would not have done. Refused: a rule that is judged (one that waits for a label, or has a condition in the user's words); one whose outcome is spam (not documented for filters) or that marks read (`validateFilter` does not allow it); one whose label puts its mail in a digest, since mail a filter archives never reaches Sift to be listed; one matching a list id or the sender's name (Gmail's `from` matches words of the name and the address together), asking about a fact, or carrying exceptions; one Sift learned that archives, since a filter cannot spare people the user has written to; one whose values could change the meaning of a Gmail search; and one that another rule could overrule for the same mail (a keep rule, a judged rule, or a narrower one).
- **Where Gmail differs.** A recipient condition also matches Cc and Bcc; subject words match whole words, not substrings; a domain is written `@domain`, and several values as alternatives (`a@example.com OR @example.org`). The verdict lists these (`differs`) so they can be shown before the user asks.
- **Asking.** Adding a rule that can be a filter, while Sift is on, turns the rule dialog into an offer of the filter, in the words of Gmail's own filter list (`Matches`, `Do this`) and with where it differs from the rule; the reply to `POST /api/rules` carries it. Filters are shown with their rules, not in Activity, which is about mail. A rule's panel says whether it is one or could be, what a filter is, the press to add or take it out, and its history (a rule that can never be one says nothing about Gmail): each write and removal from `actions`, and a deletion in Gmail that a check noticed. The Rules list marks a filter with a funnel and narrows by whether a rule is one, could be, or cannot be. Nothing there is flagged: a filter edited or deleted in Gmail is the user's choice, one out of date is brought into line once Sift is on, and a change Gmail did not take is asked for again.
- **Archived by a filter means unseen by Sift.** Sync records mail that arrives in the inbox. Mail a filter archives is not recorded, counted against the rule, or unsubscribed from.
- **Writing and removing** go through `src/actions/rule-filters.ts`: validated, written to `actions` first (`filter`, `unfilter`, with no message), then read back from Gmail's list. When the call itself errors, Gmail's list is asked at once whether it went through, so the change ends done or failed; only when Gmail cannot be reached even for that is it left open for the next check. The press that asked for it says when Gmail did not take it; after that, each check while Sift is on asks again for the rule's last change, up to three times in a row (`retryRuleFilters`). A filter the account already has that does exactly the same is taken over, since Gmail refuses a duplicate. Removing a rule removes its filter first.
- **Keeping track.** At most every 15 minutes a pass lists the account's filters and records for each rule, in that mailbox (`rule_filters.state`), what it found: `active`; `changed` (edited in Gmail: left alone); `gone` (deleted in Gmail: not put back); `outdated` (the rule, its label or another rule changed, so the filter no longer does what Sift would). An outdated filter is replaced, or removed if the rule can no longer be one, while Sift is on; while it is off it is only marked, and keeps running in Gmail.

## Preferences

Everything a person prefers is in their own database.

- **Whether Sift is on, and their model** (`preferences`, `src/store/preferences.ts`): whether Sift changes their Gmail or only suggests, and which model judges it, both set under Settings. With them, the hour of their day digests arrive and the time zone it is read in ([Digests](#digests)), which Settings shows while a label digests. And whether Inbox is on (`mail`, [inbox.md](inbox.md)), set with `POST /api/mail/on`. What they want is said by their labels' descriptions and their rules; there are no free-form guidelines beside them, since the system's intent is the same for everyone and a label's description already says what belongs in it.
- **What is structured or learned:**
  - `labels`: what mail can be and what to do with each. Leave in inbox from the start; the rest chosen while setting up, from what the model suggests, and changed and added to in the dashboard, under Labels.
  - `rules`: what the user has said happens to mail, or what it is; and a rule for each sender Sift blocked.
  - `correspondents`: whether the user has ever written to an address, cached.

## Model tier

When no rule decides a message, one model call does. It is deliberately not an agent.

- **The model's only tool records its verdict, and it takes no action.** Deterministic code gathers the evidence first: the message's facts, the body (read from Gmail once and kept, in `read_bodies` for 30 days or in `mail_bodies` while Inbox is on, and cut to 4,000 characters for the model), how much mail this sender has sent, what the user said their earlier mail was (by an answer or a rule; a model's guess the user never answered is left out, so an early mistake is not handed back to the model as fact), and whether the user has ever written to them.
- **Its only output is a label** from the user's list, or `unsure`, with a one-line reason, asked for first so that the label follows from it. The reply is validated; anything else is a failed call, which is tried again on a later pass.
- **The label's action decides the outcome**, so the user's choice, not the model, determines what happens to the message.
- **Three protections apply whatever the model says:** mail from someone the user has written to is never archived or marked spam on the model's word (and "could not check" counts as yes), nor is a reply in a thread the user has written in, and `unsure` or an unknown category leaves the message for review.
- **Its label alone is carried out only at 0.9 or more** (`SURE`, `src/triage/stages/model.ts`), whatever the label does. Below that the message is held for the user with the label as the answer to agree with, so what Sift does on its own is what the dashboard's full meter promised while it was off. A rule whose condition the model found met is the user's rule and has no bar.
- **It is shown a few of the user's own answers.** Beside each message go up to six stored examples, chosen for it by what the mail is like, since one sender often sends several kinds: the newest two under the same sender name, then with the same kind of subject from anyone, then from the same sender, then the same domain (not one anyone can get an address at), then the newest of each label from anyone else, each shown once, at most two from the sender's own address, within a budget of about 1,200 tokens (`src/triage/fewshot.ts`). A name is matched with the domain that sent it (the address, where anyone can get one there), and a subject with its numbers and reply marks taken out (`subjectPattern`); both are stored on the example as keyed hashes (`exampleKeys`, `src/store/content.ts`), so each way is an indexed lookup of the newest two (`examplesFor`, `src/store/examples.ts`), and only the six picked have their text read. Answers from before there were these hashes, and every one under a new key, are hashed by the start-up pass. An example's text starts after the lines that link to its web copy ("View this email in your browser"). Each is only a line of its facts (`factLine`: Gmail's category, how it was addressed, bulk signals, DMARC; only what is there), sender, subject, the first 300 characters and the owner's label, fenced as untrusted like the email itself, with every field JSON on one line so an example's text cannot close its fence or forge a label. It is always on; a test run can leave examples out, to measure what they add.
- **The prompt marks the email as untrusted** and keeps it apart from the labels and the header facts. The labels come first, then the examples and the user's rule for the sender, and everything about the email last and together: its facts, then what its sender wrote. Every line of its body starts with `| `, so no line of it can end the email or pass for a section of the prompt; what the sender wrote into a header (a list id) is quoted. The worst an injected email can do is get itself given the wrong label, which the audit log can undo.
- **Learning:** the model only says what mail is, so the user giving a label's mail another action (moving a sender's Notifications back to the inbox, archiving their Account alerts) is something no example teaches it. Two such answers in a row for one sender and label propose "from them, when it is L → that action" (`proposeFromCorrections`, `src/store/proposals.ts`); an answer that went with the label breaks the run. Nothing changes until the user accepts it. A sender who already has a rule for all their mail, or for that label, is left alone, and so is one whose proposal the user dismissed.

Models are reached through pi-ai (`src/model/`, the only module that imports it). **Each person signs in and chooses their own,** under Settings, so their mail is judged on their account and at their cost; a pass builds each person's tier from their database (`openModelTier`, `src/sift/controls.ts`). Without a model, mail no rule covers waits, undecided, for one. The ways in (`modelChoices`) are ChatGPT and an API key for OpenAI, Anthropic, OpenRouter or Vercel AI Gateway. An install signs people in to ChatGPT one way, its `SIFT_CHATGPT_SIGN_IN` setting. By default it is a device code (`openai-codex`): the page shows a code to enter at OpenAI, nothing has to come back to this server, and calls go to Codex's backend at `chatgpt.com`, which OpenAI does not document for other tools. Sift asks for the code and checks whether it was entered itself (`checkChatGPT`, `src/sift/chatgpt.ts`) as the page reloads, at most once per OpenAI's interval, where pi-ai's own login loops, and stores the credential in pi-ai's shape. `redirect` is OpenAI's Sign in with ChatGPT (decided 2026-11-15), on its documented API at `api.openai.com/v1`, billed to the person's plan. It needs no app registered: each sign-in registers its own client, under the install's device id. But OpenAI only ever sends the browser back to `http://127.0.0.1:1455` on the person's machine, never to a hostname, so the person lands on a page that does not load and pastes its address into the dashboard. Sift listens on no port for it: pi-ai's own login does, so Sift builds the sign-in and exchanges the code itself (`startChatGPTRedirect`) and stores the credential in pi-ai's shape, which pi-ai then refreshes. A sign-in takes the address for 10 minutes, and a wrong one can be followed by the right one. It is registered as its own provider, `chatgpt`, so it can sit beside an OpenAI key; pi-ai recognises a ChatGPT token only on its `openai` provider, so `chatgptProvider` sends each call as that provider's. Only the install's way is registered, so switching signs everyone out of ChatGPT. The two resellers list hundreds of models; only the major labs' small ones are offered (`offerModel`). Choosing a model starts on the newest of the provider's cheapest family, already chosen; Change shows the newest of each of its few families (`shortlistModels`), each with what 1,000 messages would cost at its catalog price (`priceOf`), for calls the size the person's have been lately (`averageCall`, `src/store/runs.ts`) or a typical one, and the full list folded under them. A ChatGPT plan is not charged by the message, so through it every price (here, the Model row, going through the inbox) and what the model has cost (marked `≈` where a figure stands alone, with the reason said once where it is shown: the card of Sift's line, Settings' last 30 days, Rules' Cost 30D, a rule's panel, Activity's and a rule's cost line) is said to be at API prices, which the plan covers. A message's history marks a call by the way it went, so one made before switching to ChatGPT stays a price paid. What each says is in `web/src/lib/prices.ts`. How hard the model thinks before it answers is the person's choice too, under the Model row: low (the default), medium or high (`REASONING`, `src/model/reasoning.ts`), sent with every call as pi-ai's level, which gives a model that cannot do one the nearest it can. Given none, pi-ai turns reasoning off. One provider is in use at a time. Changing it signs in to the new one beside the old, chooses its model, and only then signs out of the old, so a model is in use throughout. Until a model is in use and signed in, and every mailbox has a label of its own, every screen of the dashboard is the setting-up steps (`SetUp`, `web/src/components/set-up.tsx`, on the `Onboarding` page): connect a model, say what you want, choose your labels, and go through recent mail to answer. A step already done is ticked and skipped. When the model in use is lost (its sign-in removed or expired), only that step comes back, under "No model connected". Without them there is nothing to suggest, and the screens would only show it. Settings is a panel over any screen, setting up included (`?settings=1`, from the account menu or from the setting-up page), so nothing has to be finished to reach it. Sign-ins are kept in the person's database, through a port (`SignIns`, `src/model/credentials.ts`) so `src/model/` never touches the store. Keys in the environment are never used: they would speak for everyone. Adding a provider means adding it in `openModels` and to `modelChoices`. pi-ai depends on every provider's SDK; the ones Sift cannot call (AWS, Google) are removed from the install by `overrides` in `pnpm-workspace.yaml`, so a new provider may also need its SDK put back there. pi-durable is not used: a triage run is one call, and a message with no decision is found again by the next pass.

There is no shell and no filesystem here. A sandboxed agent with those is planned only for a possible operator-facing assistant that does open-ended analysis.

## The command line

Five commands: `init` sets Sift up, `run` reads and classifies mail and serves the dashboard, `status` says what is set up, `dev` is `run` for working on Sift, and `reset-db` moves the local database aside. Everything else (rules, labels, the log of changes, undo, choosing a model) is in the dashboard and has no command. Options are in [cli.md](cli.md).

## Home directory

Everything Sift keeps is in one directory, the home: `~/.config/sift` by default (`$XDG_CONFIG_HOME/sift`), or wherever `--home` or `SIFT_HOME` points (the Docker image uses `/data`). Keeping settings, the database and credentials together means it can be backed up or moved as a unit. Settings are environment variables (`ENVIRONMENT`, `src/config.ts`), each checked when Sift starts; none is needed. Locally they sit in the home's `.env`, which `sift init` writes one line at a time; a variable already set in the environment wins.

- `.env`: settings, only what a deploy must say (`SIFT_DASHBOARD_PORT`, `SIFT_URL`, `DATABASE_URL`, `DATABASE_MIGRATION_URL`, `REDIS_URL`, `SIFT_CHATGPT_SIGN_IN`, `SENTRY_DSN`, `SIFT_CLOUD`). Optional; read at start, before the one in the working directory, and neither replaces a variable already set. A wrong value is an error that names its variable; a misspelt variable is not seen. Command-line flags override them for one run. What a person chooses is in their `preferences`; how often Sift looks and how long it keeps things are constants in the code.
- `database/`, `database.lock`: the database, when it is PGlite (see State).
- `google-client.json`, `dashboard-key`: the install's Google client and the session secret, owner-only. People's sign-ins are in their databases. Where no file is kept (Vercel), the session secret is `SIFT_SESSION_SECRET`; the id ChatGPT knows the install by is derived from it.

**Credentials are encrypted with a key from the environment** (`SIFT_KEY`), because a key stored beside them would protect nothing. See [secrets.md](secrets.md).

- Every one is encrypted and decrypted through `src/secrets.ts`, which knows ciphertext and nothing about what is inside. Each is bound to what it is for (a file's name; a row's person, kind and key), so it cannot be moved into another's place.
- Each value records the id of the key that encrypted it. `SIFT_OLD_KEYS` are accepted for reading; a value is re-encrypted with the current key whenever it is written, and `sift run` re-encrypts all of them at start, in files and in every person's database, and encrypts any still plain, so an old key can be retired. On Vercel the build does it for the database, after migrating (`src/vercel/migrate.ts`), so a key set or changed there takes effect with the next deploy.
- A credential whose key is missing stops `init`, `run` and `status` at start, naming it. The alternative is a sign-in that stops working for no visible reason.
- Without a key Sift runs as before, storing them plain, and says so at start.
- So is what came from mail, and everything that names a sender (`src/store/content.ts`): the text and HTML Sift holds, each record's headers (its sender, recipients, subject and list id are read from them, `envelopeOf`), a rule's conditions, name and Gmail filter, proposal conditions, a change's details, a decision's reason, and the person's words to the label and rule models with what those suggested. Senders, domains and conditions are found by a keyed hash per person (docs/security.md); a record's facts say only whether it has a list id. Search and sorting by address decrypt in Sift, not in the database; Inbox's search first narrows by a keyed Bloom filter of each message's words, and decrypts only what it lets through ([security.md](security.md#the-search-index)). Who the owner has written to is kept only as hashes, so a new key empties that cache.
- `setup.json`: how far `sift init` has got, so it resumes.

`sift init` (`src/cli/init.ts`) sets all of this up. A first run walks through every step, and one stopped part-way carries on with what is missing. Once the dashboard has an address and the Google client is finished, it instead lists the steps with what each is set to and redoes the one the user picks. The key is optional, so leaving it unset does not bring the walk-through back. The model is not here: each person signs in to their own in the dashboard.

## Teaching

Sift suggests first and acts second. While it is off, every decision is a suggestion, and the dashboard's For review page is where the user teaches it.

- **A suggestion** is the current decision for a message, recorded as a suggestion, that the user has not answered. So is mail Sift left for the user while on (`review`, carried out as the review label in Gmail): it stays on For review until answered, a rule or label changing does not decide it for them, and answering it takes the review label back before the answer is carried out. Decisions that only repeat what the user already said (their answers, marked `by_user`, and rules they wrote or made by correcting Sift) are not suggestions; ones from a rule Sift learned are.
- **For review lists one message per row**, newest received first under Today, Yesterday, This week, Last week and then the month, except that a sender's waiting mail Sift gave the same label under the same name, in any of the person's mailboxes, is one row, standing where the first of it does, with how many and their subjects; its answer is for all of them (`fold`, `web/src/lib/fold.ts`). Mail Sift could not place is never folded. The answer is a dropdown that starts on the label Sift gave, with a meter for how sure it is, and a check that commits it; Leave in inbox is always its first choice, set apart, then Sift's label and the likely ones, then the rest. The meter is full only for what Sift would do by itself once on (a rule, or a model at the bar), never for mail it would hold. While Sift is off, For review opens with what that means: nothing in it has been done, and the full meter is what Sift will do on its own. The dropdown has Leave in inbox first, then Sift's label and the labels the sender's other mail has had (most first), then every other label. The model gives one label today, so the sender's history stands in for its runners-up.
- **An answer says what one message is, and that is all it says.** Like a spam button with more outcomes: Sift records the label, does what that label does to the message in Gmail (see Off is the default), and keeps the message as an example the model is shown next time. It makes no rule. Mail that is what Sift says but should not be moved is not relabelled, which would teach the model something false. The panel's "Keep as Marketing…" opens the rule dialog on "from this sender, when it is Marketing → Keep"; adding that rule also answers the message as Marketing, kept, so it counts as right and is put back if Sift had moved it. Keeping mail its label would move drops the label's unsubscribe and mark read (`labelled`). When the sender has other mail waiting that Sift guessed the same way, the dashboard offers the same answer for those in one press. Mail the model could never judge is answered the same way from its panel: the answer is its first decision, recorded as an answer to mail Sift had no suggestion for.
- **Every answer is scored.** `feedback` records right, wrong, or "answered" (Sift had no suggestion, which is not a mistake), per decision. The summary (`GET /api/summary`) reports it for the window per tier and per label, with which labels Sift took for which; no page shows that yet, only each label's own record on Labels.
- **Contacts lists everyone the person has mail from** in the mailboxes the switch shows, newest first (`GET /api/contacts`, `listContacts`, `src/dashboard/queries/contacts.ts`), and a sender's or domain's page is one of them. Senders are found only by keyed hash, so it groups the record by `sender_hash`, matches rules to them by hashing what each names, and opens only the newest message of each sender on the page shown, or of everyone when searching. Mail the person sent from Sift is recorded under their own addresses and left out. What a row and their page say their next mail gets is one function (`nextOf`): the rule for all their mail, else what their mail is now with the reader's answers in place of Sift's decisions, the commonest label when there are several ("Usually"), else the newest's. Their standing is read from a rule for exactly them that says only what happens to their mail (`givenBy`). People the person writes to and who never wrote back are not in it: Sift keeps who has written to whom only as hashes of senders it has checked (`correspondents`), so it has no address for them ([TODO.md](../TODO.md)).
- **Rules come from proposals and the Rules page, not from answers.** Answers propose a rule only when they keep giving a sender's mail of one label another action than the label's (see Learning); answers that agree propose nothing. Every press that makes or changes a rule opens the rule dialog in place, started on everything that place knows (`web/src/lib/rule-start.ts`): a proposal's sender, waiting for its label and then doing what the user has been doing to it (so a model still reads each message), a message's sender and label, a message's sender waiting for its label to keep it, a fact row's sender and fact, a list. The user sees and changes it before adding. Adding replaces the rule with exactly the same conditions, if there is one, and the dialog names it. Its toast says the rule just added, in the same words, by its name if it has one; Undo on it (or Z) takes the rule back, unless it replaced one: removing it would not bring the old one back. A rule's panel has Change…, which opens the same dialog on the form, filled in with the rule; saving (`POST /api/rules/edit`) changes it in place, keeping its place in the order, its exceptions, its count and its Gmail filter (brought into line like any out of date), and makes it the user's. It refuses to take another rule's exact conditions, since which of two alike decides would come down to their order. Undo on its toast saves the rule as it was. A standing (Trust, Unwanted, Block on a sender's or domain's page) is the exception: it is only that address or domain and what happens to their mail, so it is given in one press (`POST /api/standing`), its toast with Undo and, unless it keeps mail, Apply to inbox. It replaces another standing, which Undo gives back, but never a rule for them that says more (a label, an exception, an extra): that press opens the dialog on the standing instead, which names what it replaces. Taking a standing back is one press. The answer endpoint (`POST /api/feedback`) takes one message and makes no rule.
- **Any decision can be answered, not only a suggestion.** Every list opens a message in the same panel: Sift's label as the answer to agree with, what else it might be, its reason, the message, and what Sift knows about the sender. Answering a message Sift had already decided records the user's answer as a new decision for it and, if Sift had changed the message in Gmail, takes that change back so the new decision is carried out from where the message started.
- **A waiting suggestion follows the rules and labels as they are now.** When a rule or a label changes in the dashboard, each waiting suggestion is run through the rules again, with no model (`src/learn/redecide.ts`), and a new decision is recorded where the answer differs: a rule of the user's now decides it, so it stops being a suggestion; its label now does something else, so the same label is recorded with the new outcome (and mail is never newly hidden from a sender who was not checked); or the rule that had decided it is gone, so it goes back to what a tier said before, or to review. Mail Sift marked for review in Gmail while on is settled only by a rule of the user's that decides it by itself, with no model: that is recorded as the user's press, Sift's review mark is undone in Gmail, and the pass the change starts carries the rule out. What a model decided, worked out again, keeps that call's run. Mail the user answered for is never touched, even by an answer given while this runs: it is one transaction, and each message is checked again, its decision row locked, just before its new decision is recorded. Mail a rule decided when it arrived stays as history.
- **A rule can be applied to the inbox as it is now.** A rule decides mail from then on, and re-decides what is waiting; while Sift is off, what it decides is not carried out either. A rule's panel charts what it decided each day over 30 days, carried out or not, and what checking its condition cost (`GET /api/rules/usage`); it lists what it decided that is still waiting (`GET /api/rules/waiting`), and opens wherever a rule has just been made; the rule dialog's "Apply to mail already there" (ticked by default) goes on to the look below. "Apply to inbox" searches Gmail for what the rule names (`inboxQuery`, `src/work/apply.ts`: sender, recipient and list, not the subject, since Gmail finds whole words and a rule's subject may be part of one; values that could change a search's meaning are left out, which only widens it) and checks the rule on the newest 20 it finds, from the record for mail Sift has recorded and from Gmail's headers for the rest, which it records then, decided already and out of the triage queue (`recordFound`), so no look reads it again. Before anything moves it shows the newest five the rule decides and how many it would: exact when the search found no more than it checked, and otherwise that share of Gmail's `resultSizeEstimate`, which is rough, so the page says "about"; with how many a model must read first, and what that costs. Nothing is decided until the press. Gmail's search for it is kept 5 minutes (`counted`, `src/sift/controls.ts`), so opening it again, or a reload with it open, asks Gmail nothing. The press (`POST /api/rules/apply`) starts an inbox run for the rule (below, `rule_id`; one per rule at a time, refused while one goes), Sift on or off: it lists everything the search finds, up to 10,000, and applies the rule to 250 a tick (`continueRuleRun`, `src/work/inbox.ts`), with no model. The rule's panel shows how far it has got, with Stop (`POST /api/inbox/stop` with the rule); a removed rule ends its run. On each message the rule is checked again: what it decides is recorded as the user's press (`carry_out`, `by_user`) and carried out on the pass the press starts; mail a model must read is recorded with `messages.apply_rule`, and once the model has said what it is, what that rule decides is carried out the same way, while anything else it turns out to be is handled as new mail. Mail the user answered for, mail with a decision still waiting to be carried out, and mail another rule decides are left out, and so is mail on which Sift already made the change the rule would. Mail Sift decided and changed while on (marked for review, given a label it keeps in the inbox) is not: Sift's change is taken back first (`takeBack`), then the rule's recorded.
- **Every marked message becomes an example.** The answer creates an `examples` row with the text and HTML Sift holds of the message (`exampleText`: Inbox's, or what it read in the last 30 days), the text cut to the model's 4,000 characters; the read text stays its month. Where Sift holds none, the next pass reads the message if Sift never read it, and otherwise keeps the answer alone (`gone`), since its text was let go 30 days after reading and is not read again (`captureExamples`). These are the evaluation and training set. A message that has since been deleted keeps its answer and is marked gone.
- **Gmail teaches too.** Each sync reads what the user did to messages Sift has decided (`learnFromGmail`, `src/learn/gmail.ts`), and records it as an answer from the dashboard is recorded, marked `via = gmail` in `feedback`:
  - Where the message is now is the outcome the user wants: its labels in the record, which the same history has just brought up to date (`followLabels`), with no read of Gmail. A move does not say what the mail is, so the label Sift gave stands (and counts as right) and the outcome is recorded as the exception; a different `sift/…` label put on it is a correction of the label.
  - The new decision is the user's (`by_user`) but is not carried out, whether or not Sift is on, so Sift does not then move a message the user has just placed.
  - While Sift is off, the user doing in Gmail what Sift suggested counts as agreeing.
  - Skipped: mail Sift could not place and the user did not label (there is no label to record), trashed mail, mail history says was deleted, and mail Sift never recorded.
  - The same history read twice records nothing new: an answer is only recorded when the message's place and label differ from its current decision and from the answer already on it.
  - Not seen: anything done while the history cursor was expired.

- **Examples are kept until the user deletes them**, one at a time or all of an account's, or for 365 days after the answer (`EXAMPLE_KEEP_DAYS`, `src/store/examples.ts`); each person's daily upkeep deletes the ones past it. Deleting an example removes the stored message only: the answer stays in `feedback`.
- **Examples test the model.** A test run replays the model over an account's stored examples and scores it against the user's answers: right, wrong, "unsure" and failed calls overall and per label, which labels were taken for which, and cost and tokens per message. It is started from the dashboard and never by Sift itself, because every example is a paid model call; a run takes at most 200 examples, newest answers first, four calls at a time, in the background. Each example is judged on what is stored (the recorded headers, the example's text, how much the sender had sent by then, and whether the user has written to them; no standing and none of the sender's other labelled mail, which new mail is shown), so Gmail is not asked and the user's later answer does not leak in. A run records what it ran with (model, a hash each of the prompt layout and the labels, and whether examples were shown) and one row per example, so two runs can be compared example by example. With examples shown, only those answered before the message arrived are in its prompt, as new mail would have had: answers given later (often in one go for a sender's waiting mail) would show the model the answer to a message just like it. Answers that had an example from the same sender are counted apart, since a sender the user has already answered for is easier than a new one.

Code: `src/learn/feedback.ts` (suggestions, answers, accuracy), `src/learn/gmail.ts` (telling the user's changes from Sift's, answers from Gmail), `src/work/examples.ts` (capture), `src/learn/evals.ts` and `src/triage/score.ts` (test runs).

## State

One Postgres database for everyone: Postgres is the one engine Vercel and a local install both have. Locally it is PGlite, Postgres compiled to WebAssembly and run inside Sift, keeping its data in `database/` in the home directory; given a Postgres server's address (`DATABASE_URL`), Sift uses that instead. Given also the address of the role that owns the tables (`DATABASE_MIGRATION_URL`), Sift migrates as that role, grants `sift_app` to the first, and runs as it: a role that owns nothing cannot change the tables or turn their policies off.

- **Schema and migrations.** The schema is `src/store/schema.ts` (Drizzle). `pnpm db:generate` writes each change as a migration in `src/store/migrations/`, which Sift applies when it opens the database (Drizzle's migrator); what Drizzle cannot say (grants, `FORCE ROW LEVEL SECURITY`) is a custom migration made the same way (`drizzle-kit generate --custom`). A test fails when the schema has a change no migration covers. A database last opened by a newer Sift is refused, and so is one made by migrations since replaced (Drizzle would otherwise run ours again over its tables). Drizzle orders migrations by when they were made, so when two branches each add one, generate again on the merged branch rather than keep both.
- **Who sees what.** `users` and `accounts` say who the people are and which mailboxes are whose. One mailbox of each person's is their primary one (`accounts.primary`, at most one by `accounts_one_primary`): who they are, whichever they signed in with, and the address the page names them by and anything sent to them would go to. It is their first, chosen under Settings (`POST /api/mailbox/primary`), and removing it hands it to the one of theirs connected longest (`removeMailbox`). Every other table holds one person's data: it carries `user_id`, filled in from the transaction's `sift.user` setting, and has row-level security, forced even for the tables' owner, that shows and accepts only that person's rows. Foreign keys include `user_id`, so no row can point at another person's. Every query runs in a transaction that first becomes `sift_app`, a role that owns nothing and cannot bypass the policies (`handle`, `src/store/sql.ts`): the central handle sees no one's rows, `store.user(id)` only that person's, `store.nobody` nothing. That is the second line. The first is Sift's own code: the handle's query builder (`src/store/own.ts`) adds `user_id = <person>` to every select, join, update and delete of a person's table, puts the person's id on every row inserted, refuses a `user_id` from the caller and a right or full join, and the central handle refuses a person's table outright. Tests check every such table has the policy, that one person cannot read or write another's rows, and that the builder holds them apart with row-level security out of the way (`tests/own.test.ts`). Locally PGlite runs as a superuser, so a statement that resets the role would escape the policies; Sift sends only what its builder makes. With a server, connect as a role that is not a superuser. See [security.md](security.md).
- **One process.** PGlite is one process's alone and does not check that itself, so Sift holds `database.lock` (its process id) and refuses the folder to another process while it is alive; `sift status` then says Sift is running. A lock left by a process that has gone is taken over.
- **Queries** are built with Drizzle's builder on the `Sql` handle, from the tables, operators and `sql` in `src/store/query.ts`; nothing outside `src/store/` imports Drizzle, and no SQL text names a table (`sql` refuses one interpolated, and a test reads `src/` for one written). `sql` is for expressions the builder lacks (`count(*) FILTER`, `coalesce`), with columns interpolated. A transaction is one call taking a function that awaits nothing but the database, since it holds the connection; using an outer handle inside it is refused rather than left to wait on itself. A failed statement reports the database's error, never the values bound to it, which can be a message's text.

Defaults are written by code, not by a migration except to bring existing mailboxes up to date (`0030` added Leave in inbox to older ones, `0034` renamed it): a mailbox's one starting row, Leave in inbox, with the mailbox (`ensureMailbox`), and a person's preferences when their database is first opened. Labels are never deleted, only marked removed, so every label a row names exists. Together the tables are the complete record of what Sift saw and did, and everything else (the dashboard, undo, future analytics) reads from them.

- **messages:** one row per message Sift has seen (with Inbox on, every message of the person's mail in the window, `decided` already where Sift does not triage it: what it copied, what arrived outside the inbox and what the person sent; `recordKept`, `src/store/kept.ts`): its headers encrypted (sender, recipients, subject, list id), the keyed hashes of its sender and domain (`sender_hash`, `domain_hash`), its labels and the facts derived from them. Its labels follow Gmail's history, which each sync reads anyway, the last change to each label standing (`followLabels`, `src/store/messages.ts`), so the record says what is in the inbox and what is unread now, for everyone, at no extra Gmail call; what changed while the cursor had expired is not seen until the message changes again. No body. This is enough to triage a message again without refetching it.
- **feedback, examples:** the user's answers, one per decision (what the mail is, what should happen to it, and whether it came from the dashboard or Gmail), and the readable text of each message they answered for, kept as evaluation and training data until deleted or a year old (see Teaching).
- **read_bodies:** the readable text (all of it, up to 200,000 characters) and the HTML of every message Sift read whole with Inbox off: what the model read, mail waiting on the user that Sift would move or could not place, and an example of mail it never read. Kept 30 days from reading whatever becomes of the message (answered, decided again, out of the inbox), so a model call tried again, the For review list (its start, under the subject), the message's panel and an answer's example read it from here and never from Gmail; each person's daily upkeep deletes what is older, whether or not Gmail can be reached (`purgeRead`, `src/store/kept.ts`, from `upkeep`, `src/work/run.ts`). Before 0070 it was `suggestion_bodies`, held only while mail waited and cut to 4,000 characters; its rows were kept as they were.
- **mail_bodies:** the whole readable text and the HTML of the person's mail, for Inbox ([inbox.md](inbox.md)): all of it within the window they chose (the last year, three years, or everything; `preferences.mail_window`) and whatever is in the inbox however old, held only while they have Inbox on (`preferences.mail`), and deleted in the same write that turns it off (`setMail`, `src/store/preferences.ts`). Narrowing the window deletes the text outside it in the same write. With `examples` and `read_bodies`, the only places message content is stored. A pass reads a message's text from here, then `read_bodies`, before Gmail (`heldText`, `src/store/kept.ts`): the model, the examples and the text kept of waiting mail. Each row also holds the message's search index (`search`), a keyed Bloom filter of its words, its sender's and its subject's, written with the text and so deleted with it, kept in the row (`STORAGE MAIN`) where a search scans it; null for text kept before there was one until a pass indexes it ([inbox.md](inbox.md#search), [security.md](security.md#the-search-index)).
- **mail_copies:** copying a mailbox for Inbox, one row a mailbox: the range it lists, where Gmail's listing has got and how much it has done ([inbox.md](inbox.md#data)). Deleted with the text when Inbox is turned off.
- **model_runs:** every call to the model about a message, judged or failed, with the model, tokens, dollars, when it started and finished, the error when it failed, and the rule whose condition in words it checked, met or not, which is what that rule costs (Rules shows 30 days of it). Calls made before that was recorded name the rule only where they met its condition. Cost is summed from here, so a call that failed (an unusable answer is still billed) counts. Runs no decision links to are how a message's tries are counted; an outage marks them `retried_at` (`excuseRuns`) rather than deleting them.
- **decisions:** an append-only log. Each is a suggestion or to be carried out (`carry_out`), says whether it is the user's own answer (`by_user`), and has an outcome once carried out; it is unsettled while `carry_out` and no outcome. Every triage outcome is recorded, including "keep" and "could not decide" (a model unsure), but not a failed model call, and not mail no tier looked at for want of a model, both of which stay queued. Each has the tier that made it, the reason, the confidence, how long deciding took, and the run that reached it when a model was asked. A message can have several decisions; the latest is current.
- **actions:** the audit log of every mailbox change, with labels before and after, linked to the decision it carried out. Creating and removing a Gmail filter, putting a digest into the inbox (`digest`, naming it in its encrypted payload), and mail a person sent (`send`, naming its Message-ID, recipients and subject in its payload), are logged here too, with no message.
- **digests:** each digest written: its label, the mailbox it was put in, its window (`since`, `until`), the Message-ID it was given and Gmail's id once Gmail has it, how many it listed, what the model picked (encrypted, since a reason comes from mail) with the call's model, tokens, cost or error. One a label a day at most.
- **rule_drafts:** each time the model was asked to fill in a rule, as label_proposals, with how many look-ups it made; the person's words and the rule encrypted.
- **label_proposals:** each time the model was asked for labels, with the model, tokens, dollars and the error when it failed; the person's words and the suggestions encrypted, since either may name a sender. The latest that suggested something is shown again after a reload.
- **eval_runs, eval_results:** each test run of the model over the examples, with its settings, and what the model said for each example. Labels and costs only, no message content.
- **proposals:** rules Sift proposes from the user's overrides, open until accepted through the rule dialog or dismissed, conditions encrypted.
- **labels, rules, mailboxes:** what mail can be, what Sift knows without a model, and each mailbox's history cursor and last sync time.

**Retention.** Each person's upkeep, once a day on whichever host ticks (`upkeep`, `src/work/run.ts`), deletes each message that nothing has happened to for 365 days, with its decisions, actions, model runs and answers (`RETENTION_DAYS`, `src/work/retention.ts`; well past sync's 7-day recovery search, which could otherwise bring back a message already forgotten). Keys into `messages`, `decisions` and `model_runs` do not cascade, so `pruneOld` names what it deletes and a new table that references them fails the prune until it is added there. What it costs: a change older than the window can no longer be undone from Sift, and the model is told less about how much a sender has sent. A message is kept, however old:

- while it waits in the queue to be decided. Mail the model ran out of tries on is not waiting: once its last try is as old, it goes;
- while its example is kept. Once the example is deleted or a year old, the message and its answer go like any other;
- while a decision for it waits to be carried out, or a change to it was never confirmed;
- while it holds the record of an unsubscribe, which is how Sift knows not to ask that sender again.

A suggestion still waiting is spared for 365 days from its decision, like any decision, and no longer.

While Inbox is on it keeps the person's mail instead of a year of it: a message in the inbox, however old, and one received within the window they chose, is not forgotten, and nor is anything recorded about it (its decisions, changes, model calls and answers go with it, not before it). What falls outside the window goes as above, its text first: upkeep deletes the text of mail outside the window that a recent decision or change still keeps the record of. Mail Inbox recorded and Sift never triaged (`decided` with no decision) goes by when it was received alone, once outside the window or, Inbox off, a year old. With all of it chosen, nothing is forgotten by age. Upkeep deletes each table's rows for up to 5,000 messages in one statement each, since narrowing the window can let go of many thousands at once.

Not per message, and kept until removed: labels, rules, proposals, correspondents, test runs, label suggestions, rule drafts and Inbox's Asks (`label_proposals`, `rule_drafts`, `mail_asks`, one row per model call), digests, preferences, mailboxes and sign-ins (`credentials`). Removing a mailbox or deleting a person removes all of theirs (see Deleting).

Postgres reuses the freed space; the files do not shrink.

**Deleting.** Removing a mailbox and deleting a person are each one statement (`removeMailbox`, `deleteUser`, `src/store/accounts.ts`). Every table with an `account_id` has a key to `mailboxes` that cascades, and `mailboxes` one to `accounts`, so deleting the `accounts` row takes every row of that mailbox; every table with a `user_id` cascades from `users`. A test fails when a table with an `account_id` lacks the cascading key. The mailbox's Gmail sign-in is revoked at Google first (`Controls.revokeGmail`); failing to reach Google does not stop the removal, and the person is told. Then its token is deleted from `credentials`, then the account. Deleting a person does that for each of their mailboxes and deletes the `users` row, model sign-ins included. A person's only mailbox is how they sign in, so it is never removed on its own: the page disables its trash can and the server refuses; deleting the account is its own step. When the owner is deleted, the earliest person left owns the install; with nobody left, whoever signs in next does. Gmail filters Sift wrote stay in Gmail, and its labels stay on mail. A pass that reaches a mailbox or person deleted meanwhile skips it without reporting it, and the run loop forgets them.

### Dashboard

The dashboard is where the user watches Sift, teaches it and manages it. One Next.js app serves it (a JSON API in `src/dashboard/`, handed each request by a route handler, and the page from `web/`) and reads and classifies mail, under `sift run` and on Vercel alike.

**Who may use it**

- **Someone signed in with Google as a connected account.** One sign-in does both jobs: it gives Sift its access to the account (the Gmail scopes and a refresh token) and it proves the viewer owns that account. There is no separate login and no terminal step. The page and its files are public; every `/api/` route needs the session. So are `/terms` and `/privacy` (`web/src/views/legal.tsx`), which Google reads before it lets anyone outside the test list sign in, and `/security` beside them; the sign-in screen links to all three. They exist only on a Sift run as a service for other people, which says so with `SIFT_CLOUD=true`, handed to the page by the public `/api/session`. They send questions to the repository's issues and security reports to its private vulnerability reporting, until the service has an address of its own (TODO.md). Which host runs Sift does not decide it (a Vercel deploy can be one person's, and `sift run` on a server can serve a family), and who may sign in is set in Google's consent screen, which Sift cannot read. On someone's own copy the pages would speak to its own owner, so there are none, their addresses are the dashboard's, and the fine print is only the link to the source. They speak for whoever runs the install, and what they say Sift reads, keeps, sends and protects must stay true when that changes.
- **Users and their mailboxes.** A user is a person; an account is one of their mailboxes, an identity they signed in with (`users`, `accounts.user_id`). The first sign-in makes the first user, who owns the install. Someone signed in can connect another mailbox (Settings), which becomes theirs. An account never changes hands.
- **Each person sees only their own.** A request is given the database of whoever is signed in, whichever of their mailboxes they signed in as, and no other. The dashboard is handed `People` (`src/store/people.ts`), not the store: it finds a person by the address of their session, and opens a database only through that person's `open(id)`, which refuses any id they may not read (today, any but their own). A view of all of a person's mailboxes, such as their suggestions, is one query, since their mailboxes share their database; one that merged several people's would open each through `ctx.open`; its scope is their mailboxes (`src/dashboard/scope.ts`). Every query also takes the scope and filters by it, and `?mailbox=` on any read narrows it to one of them. Every write says whose data it touches and is refused, as if the thing were not there, when that is someone else's; a row named by id is looked for only in the requester's database, so another person's gets the answer one that never existed would. Whether Sift is on for them, their model and its sign-in, and removing their own mailboxes or deleting their account are each person's own (`touches: 'self'`, or the mailbox). With no sign-in set up (tests, tools) the request is the owner's.
- **Google says who the install is for.** Whoever the Google client lets sign in may sign in to Sift: its test users while it is in Testing, anyone once it is published. Sift keeps no list of its own (decided 2026-11-16): the test users are already one, and a published app is meant for everyone. An account Sift does not know that signs in by itself is a person of their own.
- **Sessions** are a signed cookie (HMAC with a per-install secret in `dashboard-key`), HttpOnly, SameSite=Lax, 30 days, naming the mailbox and the person. Once a day old it is issued again for another 30 when the page asks who is signed in (`/api/session`, every few minutes while it is open), so someone who opens Sift within the month stays signed in. A session stops working when its mailbox is removed, and is refused if the address has since been connected again by someone else. Removing the mailbox one is signed in as clears the cookie. A sign-in returns to the path it was started from (`/auth/login?to=`, as Reconnect does), and only ever to a path on the same site. Adding a mailbox (`/auth/login?add=1`) leaves the session as it was and returns to Settings; one already someone else's is refused, since a mailbox never changes hands. A sign-in that fails for someone still signed in is said in Settings (`?settings=1&signin=`), not on the sign-in page they would never see.
- **Google's constraint.** It returns a browser only to `localhost` or an HTTPS address on a real domain. So the dashboard is used at `http://localhost:8787`, or over Tailscale at `https://<machine>.<tailnet>.ts.net` (`tailscale serve` proxies to localhost and passes the original scheme in a header, which is believed only from this machine). At a plain hostname or address the page says where to go. The Google client must be a "Web application" one listing `<origin>/auth/callback` for each address. A Desktop app client is refused.
- **Host and origin checks.** It answers only to names and addresses that are this machine (blocking DNS rebinding), and every write must come from the dashboard's own page: its Origin, a JSON content type and a custom header.

**What it may do**

Everything that manages Sift: answer suggestions, turn Sift on or off for the viewer's own mail, choose the model, add, edit and remove labels and what happens to each, add and remove rules, write a rule to Gmail as a filter or take it out, undo a mailbox change, go through the inbox, and trigger a check.

- It changes the database directly, never a setting. A pass reads each person's choices as it reaches their mail, and a change starts that person's work at once, so nothing needs restarting.
- It never imports Gmail, the executor or the work code (lint enforces this). The few things that need them (signing in, undo, Gmail filters, what going through the inbox would cost, check now, a test run of the model) are passed in by the process as `SignIn` and `Controls` (`src/dashboard/controls.ts`), so every mailbox change still goes through the executor and the audit log.

**What it counts.** Messages, not decisions: a message is counted once, where Sift first decided it, so an answer or a decision made again after a rule changed does not count it twice. "Without a model" is those Sift first decided with no model call (not the user's own answer); a model's cost is "for" every message it was asked about, failed calls included. Not done, in Activity, is a change that failed or was never confirmed; one still waiting for a pass (an answer, or anything left while Sift was off) shows as waiting, among the changes.

**Going through the inbox.** Mail already in the inbox when Sift starts (copied for Inbox or not: copied mail is recorded but not decided), or that an older model or older labels decided, is gone through on request: from Settings at any time, when Sift is turned on (it asks then), and while setting up (the newest 300, enough to teach with). Before the press it says what it would take (`GET /api/inbox`, `inboxEstimate`): Gmail's count of the inbox (`users.labels.get`, kept 5 minutes, since Settings and setting up open with it), capped at 10,000 a mailbox (`REACH`, `src/store/inbox.ts`); how many need the model, at the share of the person's decisions in the last 30 days a model was asked for; and what that costs, at what one message costs them (`costEach`, `src/sift/controls.ts`, which also prices applying a rule): what their last 200 answered calls on that model averaged, or with fewer than 20, their usual call's tokens at its catalogue price, or a typical call's. Through ChatGPT that is what the same use would cost through the API: pi-ai records each call's cost at that price. The press (`POST /api/inbox/start`) makes an `inbox_runs` row per mailbox with a label of its own; one at a time per mailbox, which the database holds (`inbox_runs_one_going`, which also allows one run per rule applying it). This is the one way Sift works through many messages in the background: a row per run, never per message, gone on with a slice per tick and capped at `REACH`. A tick finds each run not finished and goes on with it (`continueInboxRun`, `src/work/inbox.ts`): it lists the inbox's ids, newest first, into the row, then decides 250 a piece, four model calls at once, each as a pass would decide new mail (the cascade and the model's run, the decision recorded, carried out where it may be). Mail the user answered, a decision waiting to be carried out, and anything decided since the run began are left. Mail Sift never saw is fetched and recorded first, without moving the sync cursor. Whether it changes Gmail is whether Sift was on at the press (`acts`) and still is: started off, it only suggests, even once Sift is turned on, and its new mail is recorded `suggest_only` so a pass that reaches it first does not act either; turned off meanwhile, it stops acting at once. Where Sift's own change to a message still stands (a label it added, `sift/review`), a different decision takes that back before it is carried out; the same decision changes nothing. A model that fails decides nothing, as in a pass; once the provider looks down, what it was not asked about waits for the next piece, in order. Without a model it waits. Stop (`POST /api/inbox/stop`) finishes it where it is, leaving runs applying a rule. Settings shows how far it has got, what it has spent (the model's runs on its messages since it began) and about how long is left; until it is finished, For review says mail is still coming instead of that nothing waits.

**The page**

- **What is encrypted is drawn only in the browser.** What `src/store/content.ts` decrypts comes out `Confidential` (`src/confidential.ts`): the string itself at run time and in the JSON, opaque to the type checker, so React takes it neither as a child nor as an attribute. The API's reply schemas type each such field `held` (`src/dashboard/types.ts`), and the page's types are those schemas, so the page draws one only through `reveal` (`web/src/lib/reveal.ts`). That module imports `client-only`, so `next build` fails when a server component reaches it, however far down. The server reads one as text through `plain` (`src/plain.ts`), for the model, search, rules and Gmail filters; the linter refuses that module in the page, the frame, `triage/`, `model/`, `gmail/` and `telemetry.ts`, and refuses a template literal or `String()` of an unrevealed one. A rule's facts and a reply's literal words are Sift's own, and stay plain.
- **Untrusted content.** Subjects and sender names come from email. React renders them as text, and the page sets no HTML from a string (`react/no-danger`); a message's own HTML is shown only in a sandboxed frame under a policy of its own (`FRAME_POLICY`). The page and its files are served with `PAGE_HEADERS` (`src/dashboard/policy.ts`, through `next.config.js`): no other site may frame it (`frame-ancestors 'none'`), no referrer leaves it, since a sender's page has their address in its path, and nothing is read as other than it says. A content security policy for the page's own scripts, with a nonce per request, was dropped on 2026-11-17: it only backed up React's escaping and that lint rule, and it made every page drawn per request.
- **A message as its HTML.** Wherever Sift holds a message's text (`read_bodies`, `mail_bodies`, `examples`) it holds its HTML part beside it (`body_html`, as the message carries it, null when it has none), both encrypted with the install's key (`src/store/content.ts`, docs/secrets.md), so the panel knows which it has and never asks Gmail. The panel shows the HTML in a frame, or, chosen per browser (`localStorage`), the text. The page never holds that HTML: the frame loads `GET /api/message/html`, which reads the HTML Sift holds for one of the viewer's own messages, cleans it (`src/dashboard/mail-html.ts`) as it is sent, and logs nothing. Its response has its own policy: `sandbox` with only `allow-popups allow-popups-to-escape-sandbox` (no script, no origin of its own), `default-src 'none'` with inline styles and `data:` images and fonts only, `frame-ancestors 'self'`, no referrer, no DNS prefetch. So no image, font, stylesheet or tracking pixel loads from anywhere. The cleaner is the second wall: it rebuilds the document from the tags it read, dropping scripts, frames, objects, forms, `base`, `meta`, `link`, svg, event handlers and any link that is not `http(s):` or `mailto:`, and opens every link in a new tab with `rel="noopener noreferrer"`. It drops remote `src`, `srcset` and `background` itself and leaves CSS `url(...)` to the policy, which catches every spelling. The page's own policy gains only `frame-src 'self'` for it. The toggle is offered, and the HTML shown first, only when Sift holds HTML for the message (`hasHtml`); mail with only text, or mail Sift holds nothing of, never shows the frame.
- **Stack.** React and Tailwind, with Sift's own design system (`web/src/system`, [design.md](design.md)). Behaviour that is hard to get right (the select's list, the drawer's focus trap) comes from Base UI's unstyled primitives, wrapped inside the system's parts so no screen imports them; the look is all Sift's. Base UI's style injection is turned off in `main.tsx` for the content security policy, with its one rule moved into `index.css`. The chart is drawn by the system itself, so there is no chart library.
- **Data.** `web/src/lib/api.ts` is the only file that talks to `/api/`. Reads go through TanStack Query: cached in memory only (mail data is never written to the browser's storage), refreshed on an interval, on returning to the tab and after any change made from the page. A request that gets no answer, or an answer only from something in front of Sift (a proxy's 502 page, not JSON), marks Sift unreachable: a `Notice` over the page's title says so and the screens do not, every query pauses with what it last loaded, and the page asks again until something answers, then refreshes. While unreachable a change is refused where it was made, never queued, so nothing happens later that the user did not see.
- **Addresses.** Each screen is a route of its own in `app/` (`/`, `/inbox`, `/contacts`, `/activity`, `/labels`, `/rules`, `/system`, `/terms`, `/privacy`, `/security`), and any other path is missing (404). A sender's page is `/sender/<address>` and a domain's `/domain/<domain>`, each from all of the person's mailboxes and both under Contacts; `next.config.js` rewrites both to one page each (`app/(addressed)/sender`), drawn once for all of them, which reads the address from the address bar once it has started, so no address is in the HTML or in Next.js's payload, which for a page drawn per request holds its path. A rule's own address is `/rules/<id>` and a label's `/labels/<id>`: the list with it open, rewritten to the list's page and read from the path the same way (`useOpened`, `web/src/lib/params.ts`). A rule opened from elsewhere, as one just made, goes there, so Back returns to where it was made. Links between screens are Next.js's `Link` (`Anchor`, `web/src/system/anchor.tsx`), which fetches the screen behind each link in view ahead, so pressing one waits on nothing. Cache Components makes that a file: each screen is built once, and only the frame around it (`app/(dashboard)/layout.tsx`) is drawn per request, inside a `Suspense` that waits for `connection()`, so Partial Prefetching's second draw of each request reads no session. What the page draws reads the clock only in the browser (`Ago`, `useNow`): the build refuses a screen it would draw with the build's time. Search text, filters and the open message (`?message=<id>`, Gmail's id alone: the server finds which of the person's mailboxes holds it) are in the query, so a view can be bookmarked and Back returns from the reader to the list. The query is written with the History API, which Next.js follows without asking the server, and read as it is written (`web/src/lib/params.ts`), so a field that writes it keeps up with typing; a link that only changes the query does the same. Typing and stepping through a list rewrite the current history entry; only opening a message adds one.
- **Code.** The dashboard's screens (For review, Activity, Labels, Rules) are drawn on the server for whoever asked (`app/(dashboard)/layout.tsx`). It reads the session, Settings' data (`/api/manage`: labels and their counts, mailboxes and when each synced, the model, whether Sift is on, For review's count) and usage through Sift's API in its own process (`drawnFor`, `src/sift/page-data.ts`), so the session cookie, the Host check and the person's scope are the API's, in one place. Each reply is put into TanStack Query under the key the page loads it by and handed to the page (`HydrationBoundary`), so the page starts with them as if it had fetched them, keeps refreshing them as before, and asks for none of them again on arrival; Next.js's own way, data as props to client components, would have been a second copy of what the page already keeps there. A reply whose type holds a `Confidential` is refused there by the type checker, since what the server draws with is in the HTML. Signed out, the server draws the sign-in screen. Everything else is fetched by the browser once the page starts, drawn on the server in its loading state; the browser asks nothing ahead (no `useSuspenseQuery`), so the server never fetches it. Until the frame arrives the page is the name, where the rail, the masthead and the sign-in page have it, and the loading bar (`Opening`, `web/src/dashboard.tsx`): the frame's fallback, so it is in the HTML built once and painted before the server has read anything. A sender's and a domain's page are drawn once for everyone (`app/(addressed)/`), asking for the session in the browser and drawing only `Opening` until it answers, so a sign-in screen is never drawn over a dashboard or the reverse. Nothing that depends on the browser is drawn on the server: the clock, the locale, the query, touch, the clipboard and the address bar are read only once the page has started (`useStarted`, `useTouch`, `useParam`), so the first draw in the browser matches the server's. A script in the page's head (`web/src/lib/before-paint.ts`) lets go of the room a `Reserve` held for something that was not there last time, for what the server does not draw. Nor is anything of the server's in the page's JavaScript: the page takes only types from `src/`, `app/` imports only Next.js, React, `web/src` and `src/sift/page-data.ts`, and there are no Server Actions or `NEXT_PUBLIC_` variables (`.oxlintrc.json`, `tests/next.test.ts`). Each screen is its own bundle; what opens over a screen (Settings, a message, a rule) is fetched when first needed and ahead of need once the page is idle. Rendering the screens on the server was declined on 2026-11-15 (React Router 8): it shipped more JavaScript for one screen than the whole app did, and it put code that runs beside the Gmail tokens and model keys in the same files as the page. It was done on 2026-11-17 the Next.js way instead, and on 2026-11-18 the server began drawing what is not encrypted for whoever asked, read through `/api/` itself, which stays the only way in to anyone's data.
- **Installed.** The page has a web manifest and a service worker, so it can be installed on a phone or a desktop. The worker (`public/sw.js`, served as it is) keeps only the pages drawn for everyone and the built files. A navigation goes to the server first and keeps the page it gets when it is drawn for everyone (a screen drawn for whoever asked says `no-store`, and is never kept), falling back to that copy, or the sender page's, when the server cannot be reached; that page then finds Sift unreachable and says so. Built files (`/_next/static/`) are named by their content, so each is kept once fetched and served from the cache after; after each navigation the worker drops every built file no kept page reaches (through the scripts and styles it names), so an older build's files go. It never handles `/api/` or `/auth/`, so no mail data is ever kept in the browser. Both are served without a session, like the rest of the page's files. The page does not register the worker under `sift dev`, and removes one left by `sift run` at the same address. A service worker needs a secure context: `localhost` or the HTTPS address, not a plain-HTTP LAN name.
- **As an app.** Installed, the page is drawn to the screen's edges (`viewport-fit=cover`) under iOS's translucent status bar, with what scrolls under the bar covered in the page's own colour (`body::before`); the frame's edges (the rail, the masthead, the phone's menu, a panel, a dialog, the splash) are padded by the screen's safe areas (`--safe-top` and the rest, `web/src/index.css`), and iOS is given a picture of the opening screen for each iPhone (`web/src/lib/startup.ts`, drawn into `public/startup` by `pnpm startup-images` from the real page). Android's pull to reload is off (`overscroll-behavior-y`). It opens at `/?start=1` (the manifest, `app/manifest.webmanifest`, which also has shortcuts to For review, Inbox, a new message and Activity), which goes to Inbox while it is on and For review otherwise: where this browser last found it should (`sift:start`, `web/src/lib/start.ts`), before anything is drawn, or the first time once Settings' data says. The phone's menu and every `Dialog` add a history entry while open, so Android's Back closes them (`useBackCloses`, `web/src/lib/params.ts`); closed any other way the entry is taken off again, carrying down a query written to it meanwhile (a press that closed it and cleared `?apply=1`), and a press in one that goes somewhere takes its entry instead (`handOver`, `useGo`), so Back from there returns to the page under it. A dialog that opens as another closes, in the same draw (its next step), takes over that one's entry. A navigation that gets no answer within 8 seconds (a weak signal, a captive portal) gets the kept copy instead, as when offline; the sender page standing in for another says it is offline (or cannot reach Sift) and loads the page asked for once Sift answers. Nothing of anyone's mail is kept on the device for any of this: the only things a person writes into the browser's storage are their unsent drafts, kept under who is signed in, and those, the mailbox chosen and where the app opens are cleared on sign-out (`web/src/lib/sign-out.ts`). A reload comes back to where the page was scrolled (`useKeptPlace`, `web/src/lib/place.ts`, per tab), scrolling as the list is fetched back. A page whose drawing fails is `app/error.tsx` (or `app/global-error.tsx` when the root layout failed): it says so, reports to Sentry, and offers Reload, since the likeliest cause is an app left open across an update.
- **Updates under an open page.** Each build has an id (`SIFT_BUILD`, next.config.js: Vercel's deployment id, or one made at `next build`), written into the page and the server alike; `/api/session` says the server's. When it differs from the page's, the page carries on, and the next screen it goes to is loaded whole from the new build (`useStale`, `web/src/lib/build.ts`; `Anchor` and `useGo`), so an app left open for days never mixes builds. On Vercel, Skew Protection ([vercel.md](vercel.md)) keeps the old build's files answering meanwhile.
- **Look.** See [design.md](design.md). Tiers are one ink that thins as cost rises, because they are an ordered cascade.
- **Developing.** `sift dev` is `sift run` with `next dev` in place of `next start`: Next.js reloads what changes, the page and the server's code under `src/` and `app/` alike, and the minute's tick goes on calling it.
- **Layout.** `server.ts` is a web handler, `Request` to `Response`, and is what applies to every request: the Host check, the session, the scope and the checks on writes. Next.js hands it every request under `/api/` and `/auth/` (`app/api/`, `app/auth/`, `src/sift/instance.ts`), on both hosts. The host says whether the URL's scheme, which Next.js takes from `X-Forwarded-Proto`, is believed (`forwarded`). Each route is a module of its own at `api/routes/<path>/<get|post|frame>.ts`, as a `Read` or a `Write` that declares its path and, for a write, whose data it touches, or a `Frame`, a read answered with a document for a frame under `FRAME_HEADERS`. What they read from the database is in `queries/`, laid out the same way.
- **Shared types.** `src/dashboard/types.ts` defines the API's JSON as Zod schemas; the web app imports only their types.
- **Vercel's UI SDK** (`@ui-sdk/react`, announced 2026-11-12) was evaluated and not adopted yet: it is a 0.1 beta, and it injects a runtime `<style>` by default. It would do the job Base UI does now, supplying behaviour under the system's parts. Because only `web/src/system` imports the primitives, moving to it later changes those few files and no screen.

## Unsubscribing

Gmail has no API for it, so Sift makes the request a mail client would: the sender's one-click address (RFC 8058), a single POST. Unsubscribing is an extra a label or a rule carries, like marking read; a suggested label has it only where the sender never had permission, such as cold outreach. It is never a button. A pass makes the request after the decision's mailbox change has gone through, only while Sift is on, and never for a sender the user has written to. It is recorded as an action before the request, never repeated for a sender it worked for, and not retried for a week for one it failed for. The address comes from the email, so it is used only if the message passed DMARC, the address is plain HTTPS on the standard port, and it resolves to the public internet; the connection is made to the address that was checked, and a redirect is not followed. Lists that can only be left by sending an email are refused: Sift sends only what a person writes. Code: `src/actions/unsubscribe.ts`.

## Digests

A label set to Digest takes its mail out of the inbox as it arrives, and once a day one message lists it, with the few the person's model thinks worth a look on top (`src/work/digest.ts`). Sift writes it and puts it into the person's own primary mailbox; it never sends.

- **When.** At `digest_hour` (7:00 unless the person sets it under Settings) in their own time zone (`preferences.time_zone`, which the page says when a label is set to Digest, kept only if none is yet, and when the hour is set; never said, it is UTC), five minutes on, so an archive Gmail confirmed just before the hour is in the record (`scheduledBefore`, `src/digest/schedule.ts`). The timed tick finds it from the record alone (`digestsWanted`): Sift on, a label that digests, its last digest ended before that hour, and mail in its window. One run a person does all their labels (`digest:<person>`).
- **What it lists.** One digest a label, put into the primary mailbox, listing that label's mail from every mailbox of the person's, each linked to its own. Its window runs from the label's last digest to the digest hour (`(since, until]`, on when Gmail confirmed the archive); a label's first reaches back a day, or to its first such mail if that is older. In it is each message whose current decision put it in the digest, was Sift's own (not the person's answer) and was carried out. An archive undone since is not, nor mail answered for since. A day with nothing in it begins nothing, and its window stays open until there is.
- **Worth a look.** One model call a digest, shown only what each message's headers say: the sender's name and address, the subject and when it arrived, each as a line of JSON under a fence that says it is untrusted (`src/triage/digest.ts`), never a body, so nothing more is read from Gmail or stored. Its one tool records up to five picks by their number, each with a reason in a line. A reason that names a link, an address or a domain, or runs past 140 characters, is dropped and the pick kept, since it is printed under Sift's name. With no model, or a call that fails, the digest goes without; the failure is recorded on the digest and reported, never asked again.
- **The message.** Written by `writeDigest` (`src/digest/mail.ts`): the label, how many and since when, the picks, then the rest by sender, the sender with the most first, each sender's mail newest first with the same subject on one line. At most 150 are listed and the rest are one link to the label in Gmail. Times are the person's, and a digest covering more than a day gives each message's date instead. Nothing from mail is written as markup. It links back to the dashboard at `SIFT_URL`: unset, the production domain on Vercel and `localhost` on `sift run`, which opens only on that machine.
- **Safe to run again.** The digest is written down, closing its window, before the model is asked and before Gmail is; a run cut off part-way finishes one written down but not yet in Gmail as it was written, never asking the model again (`openDigests`). The insert is an action written before the call (`putDigest`, `src/actions/digest.ts`); when one never got its answer, the next looks for the digest by its Message-ID before putting it in again. One whose mail has all been answered for or put back meanwhile is dropped, and its window opens again.
- **Never taken for mail.** Sync passes over a digest by Gmail's id once Sift has it, without reading it, and otherwise by its Message-ID and the `digests` record (`knownDigests`, `isOwnDigest`, `src/store/digests.ts`), as do going through the inbox and applying a rule. So neither its arrival nor the person reading it begins a pass.
- **Not yet.** The label model never suggests Digest, rules cannot name it, there is no preview of the next digest in the dashboard, and it is daily only.

## Errors and traces

With `SENTRY_DSN` set, Sift sends errors, traces, logs and the tick's check-ins to that Sentry project (`src/telemetry.ts`, the only module on the server that imports the SDK, and `web/src/lib/telemetry.ts` in the page; lint enforces both). Unset, nothing is sent and every span is a no-op. Each host starts it once, as its server opens the host, and sends what is waiting after each response (with `waitUntil`) and each piece of work, since a Vercel instance may be frozen once it has answered. `sift run`'s command line starts it too, for what goes wrong before the server is up. The release is the commit Vercel names, or `SENTRY_RELEASE`.

- **What is traced.** Each piece of work (`sift.work`: a pass, upkeep, older mail, a test run), and in a pass one span per message (`sift.triage`) with one per tier under it (`sift.tier`), each mailbox change and unsubscribe (`sift.action`, from the executor), each Gmail request (`http.client`, its path with the ids in it as `{id}` in `url.template`; a 404 is an answer, not a failure) and any wait for the mailbox's quota (`sift.wait`), each database statement under a span (`db`, its text with the values as `$1`, never the values, sealed or not), each Redis call (`cache.get` with `cache.hit`, `cache.put`, or `db` for a lock or quota, named by the first part of the key alone, since the rest may be an address or a sign-in's secret), each outgoing request to OpenAI's sign-in (`http.client`, without the query), and each dashboard request (`http.server`, named by its route and never by the path a stranger sent). Spans use OpenTelemetry's names (`http.request.method`, `server.address`, `http.response.status_code`, `http.route`, `db.system.name`, `db.query.text`, `db.operation.name`), and a span that failed says `error.type`: the error's class or the status, never its words. Every trace is kept (`tracesSampleRate` 1): a dropped pass would lose its model calls.
- **A trace per tick, and one per piece.** The tick is a span (`sift.tick`) that begins runs; each piece is a span (`sift.work`) in its run's step, a trace of its own. Each tick, on Vercel and under `sift run`, is a check-in of the `tick` monitor, so Sentry says when it stops, fails or runs long.
- **Logs.** Each line a host logs is sent as a log too, scrubbed like the rest, beside the trace it was written in.
- **The model call** follows OpenTelemetry's GenAI conventions as Sentry's AI monitoring reads them, under the names Sentry's own pi-ai integration uses. Each agent (`triage`, `labels`, `rules`, `ask`, `digest`, and `eval` for a test run) is a `gen_ai.invoke_agent` span carrying the id of what it is recorded as (`sift.run_id`, `sift.label_proposal`, `sift.rule_draft`, `sift.ask`, `sift.digest`, `sift.eval_run`); under it, `gen_ai.chat` for each call (provider, model, tokens with cached ones counted in the input, cost, finish reason), and `gen_ai.execute_tool` for each tool call Sift carries out: a rule draft's or an Ask's `find_senders`, and the one that records the answer (`record_verdict`, `propose_labels`, `fill_rule`, `narrow_inbox`, `record_highlights`), whose span says only whether the answer was usable. Each agent span is a conversation in Sentry of its own: `gen_ai.conversation.id` is the agent, the person and the row (`rules-3-41`; a test run's message by its place in the run, `eval-3-7-12`), carried to every span under it with the agent's name, so a retry, which starts afresh, is a new conversation. The label agent's call also carries its prompt, tools and answer (`gen_ai.system_instructions`, `gen_ai.input.messages`, `gen_ai.tool.definitions`, `gen_ai.output.messages`), so its conversation reads in full in Sentry: it is asked with the person's own words and the labels they have, never mail. No other agent's does, and the scrubber drops them from any other (`SHOWS_PROMPT`). Sentry's pi-ai integration is not used: it needs a hook loaded before Sift starts, which Vercel's functions do not give, and it would record every agent's prompt and answer.
- **What identifies a span.** Whom it is for, and only by their own id and address: each request and piece of work starts a scope of its own, and `identify` sets its user to the person (`user.id`) and the address they signed in as or whose mailbox the work is for (`user.email`). Sentry puts that on every span and error in it, which is how a person's traces, errors and conversations with the model are found. A message's id, sender and domain go as `sift.message`, `sift.sender` and `sift.domain`, each the keyed hash `hashOf` gives (per person, from `SIFT_KEY`; `traceIds`, `src/store/content.ts`): the same everywhere, so one sender's traces join up, and the very hashes `messages.sender_hash` and `domain_hash` hold, so a trace is looked up here with no new column. Decisions, runs and changes go by their row ids. Without `SIFT_KEY` a hash would be the value itself, so a trace then names no message at all. A span started under another carries these from it.
- **The page.** With a DSN, the session (`telemetry` in `/api/session`) tells the page where to send, and the page fetches the SDK then, apart from its own code (`web/src/lib/telemetry.ts`). Each load and each move between screens is a trace (`pageload`, `navigation`) with the page's timings (TTFB, FCP, LCP, CLS, INP) and every `/api/` call under it; the server continues the trace each call carries (`asked`), so its `http.server` span and the database under it are in the same trace. The page picks its load's trace as it starts, so the calls a screen makes before the SDK has arrived carry it too. The frame the server draws for a page request (`app/(dashboard)/layout.tsx`) is a trace of its own (`sift.frame`), with its three reads under it, and `sift.opened_ms` when that request waited for Sift to open on a new instance. What the page sends is scrubbed in the browser: no breadcrumbs, no query on any link (it names a message, a mailbox or a sender), a sender's or domain's page by its route (`/sender/:address`), and addresses replaced.
- **Never sent:** message text, subjects, sender names or addresses, the prompt and answer of any agent shown mail (triage, a test run, a digest, a rule draft or an Ask, whose look-ups return senders), and an error's words as a span's status. Content capture is off (`dataCollection`), and no integration that would read HTTP, the database, console output or local variables is loaded, so only the spans Sift makes go out. As the second line, `scrub` runs on every span and error on its way out: it drops the GenAI content attributes from every span but the label agent's and replaces any address, anywhere but the user, with `[address]`. Errors are sent with the trace they happened in; one that Google refusing a sign-in explains (`invalid_grant`) is not sent, since signing in again is the fix. A `Refusal` the page shows is not sent either, except a failed model call asked for from the page (labels, a rule, an Ask), which is both.
